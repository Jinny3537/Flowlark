# 产品交付工作流

Flowlark 的交付单位是一份明确范围的材料包：同一组需求、选定的原型版本、技术规格和附件，加上交接说明及验收口径。团队按这份材料讨论与追溯，变更后另建交付包。

## 日常工作顺序

| 阶段 | 产品准备什么 | 研发、测试如何使用 | Flowlark 入口 |
| --- | --- | --- | --- |
| 需求澄清 | 背景、目标、业务规则、范围及不做的事项；未知规则写“待确认” | 提出技术约束、边界情况与可测试性问题 | 需求 |
| 原型对齐 | 正常流程、空状态、异常状态、权限差异，关联需求编号 | 对照需求检查交互和状态 | 项目 → 版本 |
| 材料评审 | 确认版本、补充规格书和附件、处理开放问题 | 确认实现范围、接口依赖和验证方法 | 版本工作台 |
| 研发交接 | 在迭代中选定版本，填写交付对象、变化说明、验收口径和风险 | 下载同一份材料，按需记录进度或问题 | 交付 → 准备交付包 |
| 变更交接 | 明确改了什么、影响哪些需求；创建新包并关联上次交付 | 对照前后交付，更新开发与测试范围 | 准备交付包 → 接续哪次交付 |
| 验收归档 | 保存验收口径、结果附件、遗留问题及上线说明 | 在源版本团队协作中记录结果，必要时将结果整理为附件再冻结 | 版本团队协作、交付 |

“评审材料”“研发交接”“验收归档”是用途，不是审批状态。创建验收归档包不代表测试通过，下载材料也不等于研发已接收。系统沿用版本已确认的冻结条件，因此评审用途适合保存已完成版本确认的会议材料，不是未确认草稿的评审提交入口。

## 应交付哪些文件

| 材料 | 应说明的内容 | 存放位置 |
| --- | --- | --- |
| 需求说明 / PRD | 用户与场景、业务规则、权限、范围、约束和待确认问题 | 需求正文及需求附件 |
| 产品原型 | 正常与异常流程、状态切换、交互反馈；明确原型版本 | 版本 HTML |
| 技术规格书 | 数据字段、输入输出、接口约束、权限、异常处理和验收条件 | 版本规格书 |
| 技术设计与接口文档 | 架构选择、数据模型、接口契约、迁移和兼容性；由研发维护 | 版本附件 |
| 测试与验收材料 | 关键用例、边界条件、验证环境、结果、缺陷及遗留事项 | 版本附件；协作记录用于过程沟通 |
| 交接说明 | 接收对象、此次范围和变化、验收口径、风险与依赖 | 创建交付包时填写 |

文件是否必需取决于实际需求。当前只检查文件存在性和版本确认状态，不推断业务内容完整性、不自动判定技术评审通过。技术方案、接口文档和测试用例保留为原作者的附件，不自动生成或臆造。

## 创建与下载

1. 在迭代中关联需求与选定的版本。
2. 打开“交付”，点击“准备交付包”，填写标题、唯一标识、用途及来源迭代。
3. 检查范围。空范围、重复映射、无效版本、废弃或未确认版本、缺原型、缺关联需求实体和登记附件丢失会阻止冻结；缺规格书、未关联需求会提示。
4. 从“补充材料”打开版本工作台，补齐后返回并重新检查。
5. 填写交接说明，冻结材料。服务端会再次检查，不仅依赖浏览器检查结果。
6. 在详情中查看冻结需求、版本及变更，下载单个材料或完整 ZIP。源版本入口用于查看当前协作记录，不是冻结材料预览。

ZIP 包含 `README.md` 阅读说明、`manifest.json` 清单、`requirements/` 需求材料、`versions/` 原型及技术文件。每份文件都有 SHA-256，下载时校验；校验失败会拒绝下载，需要从 Git 恢复材料。原始 HTML 的外部 CDN、API 和在线文档正文不会下载，所以不能承诺断网可用。

## 保存和兼容

新交付包的元数据在 `snapshots/<标识>.json`，独立文件副本在 `snapshots/<标识>.files/`，均随数据仓库进入 Git。先准备全部文件，最后原子发布元数据；失败不留下可见的半份交付。不存在修改、覆盖和删除交付的 API。后续源需求、规格书、原型和附件变更，不影响已冻结副本。

旧快照仍可浏览，但明确显示“仅版本引用”；没有历史副本时无法恢复当时材料，不能用当前文件补写成旧交付。ZIP 下载在内存中组装，超大附件建议拆分范围；标准 ZIP 上限为 4GB 或 65535 个文件。

## 方案取舍与后续边界

本次延续本地文件和 Git 模式，以固定材料包承担交付。优点是不用迁移团队的需求或研发系统、离开 Flowlark 也能读取文件；代价是每次冻结会复制材料，Git 中的二进制附件会占空间，且无法自动证明接收人已阅读或验收。

另一种方案是仅保存在线文档链接，可减少复制并保持编辑协同，但正文会变化、权限可能失效，无法独立还原交付。若团队需要强制签收、多人审批、电子签署、大文件对象存储或实时文档协作，应先确认角色、状态迁移、必备文件和存储规则，再扩展服务端能力。

本轮未添加强制审批和签收状态机，也未把现有版本协作记录自动写成验收结论。后续优先明确接收/退回/验收权限与规则，再考虑交付级记录和前后包内容差异。当前的上次交付关联用于人工追溯，不是自动差异分析。
