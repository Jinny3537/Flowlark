# 项目版本迭代业务重规划

日期：2026-09-08。状态：核心创建与需求关联流程已实施。

## 1. 业务定位

迭代是一个项目为达成某个版本目标组织的一轮需求交付。主流程为：选择项目 → 定义版本迭代 → 关联需求 → 创建对应冲刺 → 执行与验收 → 完成迭代。

本期按“一轮迭代对应一个冲刺”设计；冲刺是该迭代在研发平台的执行记录，不需要用户另选一个已有冲刺。一个发布版本可以分多轮迭代交付，迭代完成不等于版本已经发布。

关系约定：

- 一个项目有多个版本迭代；每个迭代必须且只能属于一个项目。
- 每个迭代必须有版本号/版本目标；对应的研发平台发布版本可以由现有版本绑定得到。
- 每个迭代直接关联多条同项目需求，不以已存在原型为条件。
- 正式创建迭代时创建一个对应冲刺，需求对应的执行任务进入该冲刺。
- 一条需求可以保留多次迭代历史，但同一执行范围只能占用一个未结束迭代；未完成需求结转时保留来源记录。
- 原型版本是需求的设计交付物，可以后补或更新；它不是迭代版本号，也不是平台发布版本。

## 2. 当前实现的偏差

已核对现有页面和本地代码：

| 当前行为 | 业务影响 | 调整方向 |
| --- | --- | --- |
| 项目可留空 | 迭代缺少明确归属 | 项目必选，从项目进入时自动带入 |
| 新建提交固定为空的 items | 创建时无法定义需求范围 | 新建流程直接选择需求 |
| items 同时要求需求、原型项目、原型版本 | 没有原型的需求不能进入迭代 | 需求关联与原型附件分开保存 |
| 可选目标发布版本、已有冲刺 | 用户需自行理解和拼装平台映射 | 以版本目标为入口，自动创建对应冲刺 |
| 需求选择和原型项目选择彼此独立 | 可能组成跨项目范围 | 前后端都按归属项目校验 |
| ready 只根据原型告警计算 | 空迭代也可能显示可交付 | 分离需求完成度、验收结果和原型风险 |

## 3. 新建迭代交互

使用宽弹窗或抽屉，按三步组织，避免继续堆叠独立下拉框。

### 第一步：版本计划

| 字段 | 规则 | 示例 |
| --- | --- | --- |
| 所属项目 | 必填；项目页进入自动带入 | 安科泸州项目 |
| 迭代版本号 | 必填；同项目内唯一 | v1.3.0-S1 |
| 迭代名称 | 必填；可依据版本号生成后修改 | v1.3.0 隐患整改闭环 |
| 迭代目标 | 正式创建必填 | 完成整改提交、复核与闭环 |
| 开始/结束日期 | 正式创建必填，结束不早于开始 | 2026-09-14 至 2026-09-25 |
| 负责人 | 正式创建必填，从所属项目成员选择 | 当前项目成员 |
| 发布版本 | 如项目已有发布版本则绑定；仅展示本项目版本 | v1.3.0 |

迭代技术标识由系统生成，不要求用户手填“2026-S12”。版本号是业务字段，技术标识保持稳定，不随名称变化。

当尚无平台发布版本时，仍可先录入本轮版本目标；平台发布版本的新建能力应在接口核实后接入，不把创建冲刺冒充为创建发布版本。

### 第二步：关联需求

- 展示当前项目需求，支持按编号/标题搜索及状态、优先级、负责人筛选。
- 表格列为：需求编号、名称、优先级、负责人、状态、当前迭代、原型情况。
- 支持批量选择、查看已选、移除；始终显示已选需求数。
- 正式创建至少关联一条需求；没有原型的需求可以正常选择。
- 已在其他未结束迭代中的需求不可直接重复选入，显示所属迭代；转移通过范围变更处理。
- 无需求时提供“新建需求”入口并带入项目，返回后保留迭代表单。
- 修改项目后清空已选需求、平台版本和负责人，重新加载当前项目数据。

### 第三步：确认创建

展示项目、版本目标、周期、负责人和已选需求，以及将创建的冲刺摘要。

- 冲刺名称默认“迭代版本号 · 迭代名称”，生成时避免重复拼接版本号。
- 冲刺继承迭代的项目、目标、周期和负责人；技术名称长度在提交前校验。
- 底部按钮：“上一步”“保存草稿”“创建迭代并新建冲刺”。
- 保存草稿至少要求项目、版本号和名称，不创建平台冲刺，明确显示“草稿”。
- 正式创建包含冲刺创建和需求任务关联结果；部分失败显示具体状态与重试入口，不能只提示“创建成功”。

## 4. 列表和详情

列表顶部提供项目筛选，支持按阶段、负责人和版本搜索。项目内部的迭代列表固定该项目。

主表列：迭代版本/名称、所属项目、周期、负责人、需求进度、阶段、对应冲刺。需求进度展示“已完成数/总数”；同步异常作为独立提示。原型风险不再替代迭代业务状态。

详情页按以下区块组织：

1. 版本概览：项目、迭代版本、目标、周期、负责人、阶段及对应冲刺链接。
2. 关联需求：主业务区，展示需求状态、优先级、负责人、执行任务及验收结果，提供关联和移除入口。
3. 冲刺执行：对应冲刺、执行进度、阻塞任务、开始/结束操作及同步异常。
4. 原型与交付物：按需求挂载原型版本、设计文档、测试材料；保留现有原型查看与发版能力。
5. 变更记录：记录需求加入、移除、结转、计划调整及平台操作结果。

主按钮按阶段变化：草稿为“完善并创建冲刺”，待开始为“开始迭代”，进行中为“变更需求范围”“结束迭代”，已完成为“查看交付结果”“创建下一轮迭代”。

## 5. 阶段与业务规则

主阶段：草稿 → 待开始 → 进行中 → 已完成；未完成迭代可取消。同步状态单独记录为未创建、创建中、已同步、部分失败、失败。

- 开始迭代：项目、周期、负责人、需求范围完整，冲刺和任务关联成功。
- 进行中调整需求：记录原因，联动冲刺任务范围；不静默搬走其他冲刺的任务。
- 结束迭代：列出完成、未完成和待验收需求；未完成项明确退回待排期或结转至下一轮。
- 已完成迭代：保存本轮范围及验收快照；发布状态单独显示。
- 取消迭代：保留历史和原型，取消对应冲刺或记录平台失败状态，释放未完成需求的执行占用。
- 同项目并行迭代允许存在，但不得重复占用同一需求执行范围。

## 6. 数据与同步调整

建议新增稳定迭代 ID、必填的业务项目 ID、迭代版本号、独立需求关联集合和原型附件集合。现有 platform/external 保留为外部映射，不再承担业务归属的唯一来源。

业务项目与研发平台项目需要稳定映射；当前本地项目 slug 与平台 projectId 不可按名称自动视为同一项目。需求所属项目也应通过该映射验证。

创建操作使用固定操作 ID，分别记录本地草稿、远端冲刺 ID、需求任务绑定和每一步结果。重试先复用成功记录；远端结果不确定时先查询，不能盲目再次创建冲刺或任务。

需求已存在同平台同项目任务时复用绑定；没有绑定时按已配置映射创建任务。被其他冲刺占用时显示冲突，禁止悄然移走。后端再次核对项目、需求归属和占用情况，避免只依赖前端筛选或提交前快照。

需求任务的发布版本跟随迭代绑定的发布版本，冲刺 ID 跟随新建冲刺；两者分别保存。执行进度取自任务，验收状态取自明确验收结果，不从“原型无告警”推断需求完成。

## 7. 现有数据兼容

- 原始数据保留；对旧 items 按需求编号去重提取关联需求，再提取原型附件。
- 已同步的冲刺沿用绑定，不再次创建。
- 项目只有在稳定映射唯一且需求归属一致时自动补齐；无项目或跨项目的历史迭代标记“待整理”，展示具体问题。
- 历史跨项目集合必须按项目拆分或人工明确归属，不能默认取第一条项目覆盖。
- 不覆盖现有未提交修改；实施时在当前代码基础上逐项迁移。

## 8. 实施顺序和验收

先完成项目归属与需求关联模型，再替换新建流程和需求主表，随后接通创建冲刺与幂等重试，最后调整状态指标并迁移历史记录。

必要验收场景：

1. 项目 A 的迭代不能通过页面或直接 API 关联项目 B 的需求。
2. 无原型的需求能够关联并生成冲刺任务。
3. 切换项目后旧需求、成员和发布版本不会残留提交。
4. 保存草稿不创建远端数据；正式创建生成一个冲刺和预期任务绑定。
5. 连续点击或失败重试不产生重复冲刺和任务。
6. 需求关联部分失败时准确提示，成功项保留，重试只补齐失败项。
7. 占用冲突在后端被拒绝，用户可定位具体需求及所属迭代。
8. 空范围、未验收或未完成需求不会显示“可交付”；结束时明确处理未完成项。
9. 历史已同步迭代保留冲刺绑定、原型引用和可追溯记录。
