# flowlark v2.0 蓝图 · 需求驱动的全链路

> 主题：**让需求成为组织与导航的主轴，而不是版本上的一个标签。**
> 地基不变：本地软件 + Git 协作，不引入常驻服务器与自建账号体系。
> 允许破坏性变更，schemaVersion 升到 2，启动时自动迁移并备份。

---

## 一、v1 的结构性局限

v1 的主线是 `项目 → 版本`。需求存在版本 JSON 里：

```json
"requirements": [
  { "code": "REQ-0275", "title": "订单批量关闭", "url": "https://..." }
]
```

这带来三个问题，都不是加功能能绕过去的：

**需求没有身份。** 同一个需求出现在 10 个版本里就存了 10 份标题和 URL。改个标题要改 10 处，改漏一处就出现两种说法。

**关系只能单向查。** 能问「这一版实现了哪些需求」，不能问「这个需求的原型演进过程是什么」——那需要扫全库，而 v1 没有这个入口。

**跨项目断裂。** 一个需求常常同时改动订单中心和营销后台。v1 里这是两个项目下互不相干的两条时间线，没有任何东西把它们连起来。

v2 要修的就是这三条。

---

## 二、核心设计决策：关联关系存在哪一边

需求和版本是多对多。关系存哪边，是这个大版本最关键的一个决定：

| 方案 | 写入点 | 问题 |
|---|---|---|
| 存在版本里（v1 现状） | 创建版本时 | 需求侧无法反查 |
| 存在需求里 | 每加一版原型都要改需求文件 | 多点写入，且和「版本是不可变证据」的语义打架 |
| 两边都存 | 两处 | 必然出现不一致，且 Git 合并时两边冲突 |

**采用：单向存储 + 派生索引。**

关联仍然**只存在版本里**——「这一版实现了哪些需求」是创建版本时自然录入的信息，写入点唯一。需求侧的「我关联了哪些版本」通过扫描全库派生，缓存在 `.flowlark/cache/index.json`，不进 Git。

这延续了 v1 里 `BASELINE` 和「展示状态不落库」的同一条思路：**没有冗余字段，就没有需要同步的东西，也就没有不一致的可能。** 代价是需求视图要扫全库，但和现有搜索一样——几百个版本是毫秒级，引索引反而会带来「什么时候重建」这个新问题。

同理，**需求状态也是派生的**：

| 派生状态 | 判据 |
|---|---|
| 未开始 | 没有任何版本关联它 |
| 设计中 | 有关联版本，但都还是草稿 |
| 已定稿 | 至少一个关联版本已成为所在项目的基线 |
| 已交付 | 所有关联项目的基线版本都带了「已交付」标签 |

允许手动覆盖（比如「暂缓」），覆盖值存 `statusOverride`，界面上明确标出「手动指定」以区别于派生值。**只有覆盖是存储的，正常状态永远算出来。**

## 三、数据模型

### 磁盘布局

```
我的原型/
├── flowlark.json              schemaVersion: 2
├── requirements/              ← 新增：需求是一等实体
│   └── REQ-2026-0275/
│       ├── requirement.json   编号、标题、描述、外部映射、状态覆盖
│       ├── spec.md            需求说明（区别于版本级规格书）
│       └── files/             需求级附件：原始 PRD、评审纪要
├── releases/                  ← 新增：迭代 / 发布批次
│   └── 2026-S12.json          一组需求 + 各自的定稿版本
├── projects/                  （结构不变）
│   └── order-center/
│       ├── project.json
│       ├── BASELINE
│       └── versions/
│           ├── v1.2.json      requirements 字段改为编号数组
│           ├── v1.2.html
│           ├── v1.2.spec.md
│           └── v1.2.files/
└── .flowlark/
    ├── oplog.ndjson
    ├── trash/
    ├── backup/                ← 新增：迁移前的自动备份
    └── cache/                 （不进 Git）
        ├── index.json         需求 → 版本的反向索引
        ├── read-state.json
        ├── offline/
        └── external/          外部需求系统的元信息缓存
```

### requirement.json

```json
{
  "code": "REQ-2026-0275",
  "title": "订单批量关闭",
  "description": "运营需要一次关闭多个超时未支付订单",
  "owner": "张小雨",
  "statusOverride": null,
  "external": {
    "provider": "jira",
    "key": "ORD-1234",
    "url": "https://jira.internal/browse/ORD-1234"
  },
  "createdAt": "...",
  "updatedAt": "..."
}
```

外部系统的标题、状态、负责人**不写进这个文件**——它们会变，写进来就是又一份会过期的副本。放在 `.flowlark/cache/external/` 里，界面上标明「来自 Jira，10 分钟前同步」。

### version.json 的变化

```diff
- "requirements": [
-   { "code": "REQ-0275", "title": "订单批量关闭", "url": "https://..." }
- ]
+ "requirements": ["REQ-2026-0275", "REQ-2026-0301"]
```

标题和 URL 移到需求实体，版本只存编号。**这是本次唯一的破坏性变更**，也是最值得的：改一次需求标题，全库一致。

### releases/2026-S12.json

```json
{
  "name": "2026-S12",
  "title": "订单批量操作迭代",
  "startAt": "2026-08-01",
  "endAt": "2026-08-21",
  "items": [
    { "requirement": "REQ-2026-0275", "project": "order-center", "version": "v1.2" },
    { "requirement": "REQ-2026-0275", "project": "marketing", "version": "v3.1" },
    { "requirement": "REQ-2026-0301", "project": "order-center", "version": "v1.2" }
  ],
  "frozen": false
}
```

`items` 里显式记录版本号而不是「取当时的基线」——**迭代是对某个时刻的快照，基线会继续往前走**。`frozen: true` 后不再允许改动，用于「已发布」的迭代。

## 四、功能模块

### M1. 需求实体与需求视图

需求成为可以直接打开的对象。

**需求详情页**要回答的问题：
- 这个需求关联了哪些项目的哪几版
- 每个项目的当前定稿版本是哪个
- 跨项目的原型演进时间线（一条线，不是几条）
- 所有关联版本的变更日志聚合（复用 v1 的累计变更算法，只是筛选维度从「版本区间」变成「需求」）
- 需求说明、附件、外部系统链接

**需求列表**：按派生状态分组，支持按负责人、迭代、外部状态筛选。

CLI：
```
flowlark req                        列出全部需求
flowlark req <编号>                 需求详情：关联版本、演进、变更聚合
flowlark req new <编号> -t "标题"    创建需求
flowlark req link <编号> <项目> <版本>   建立关联（本质是改版本的 requirements 字段）
flowlark req unlink / spec / attach
```

### M2. 迭代与发布批次

一组「需求 + 定稿版本」构成一次交付。

**迭代视图**要回答：这个迭代研发要开发的原型有哪些、每个的定稿版本是什么、有没有还没定稿的、和上个迭代比新增了什么。

```
flowlark release new 2026-S12 -t "订单批量操作迭代"
flowlark release add 2026-S12 REQ-0275            自动取当前基线
flowlark release add 2026-S12 REQ-0275 -v v1.2    显式指定版本
flowlark release show 2026-S12                    完整清单 + 未定稿告警
flowlark release freeze 2026-S12                  冻结，禁止再改
flowlark release diff 2026-S11 2026-S12           两个迭代之间的差异
```

`release show` 的关键价值是**未定稿告警**：迭代里有需求还停在草稿版本，说明它不该进这个迭代，或者产品忘了定稿。这是研发最想在迭代开始前知道的事。

### M3. 交付包导出

把一个迭代（或一个需求）的全部内容导出成**自包含的静态站点**：所有原型（离线化后）、规格书、变更日志、附件、一个索引页。

```
flowlark export release 2026-S12 -o ./交付包
flowlark export req REQ-0275 -o ./需求包
```

**为什么这是全链路里最重要的一块**：它彻底绕开了「研发测试要装 Node、要 clone 仓库」这个门槛。一个文件夹丢过去，双击 index.html 就能看全套内容，断网也行。

技术上它是 `offline` 能力的延伸：复用外链内联，加一层索引页生成。产物纯静态，可以直接扔进任何静态托管、发压缩包、或者塞进 Confluence 附件。

### M4. 角色与权限

从 [ROADMAP.md](ROADMAP.md) 的 N1 提上来。全链路必须先解决「谁能写」。

- 启动时探测 Git 远端写权限，结果缓存
- 只读用户的界面隐藏所有写操作，CLI 写命令直接拒绝并说明原因
- 探测失败时默认可写（离线办公不该被锁死）

**为什么必须在 v2 里**：需求、迭代这些新实体如果被只读用户在本地改了推不上去，分叉的破坏性比 v1 大得多——v1 分叉的是一个版本，v2 分叉的可能是整个迭代的组织结构。

### M5. 反馈回路：标注 → Issue

只读用户没有 push 权限，评论存不进仓库。走团队已有的 Issue 系统：

- 在原型上框选区域 → 填写问题 → 生成 Issue
- Issue 自动带上：**需求编号**、项目、版本号、区域截图、原型直链、相关变更日志
- 反向：需求详情页展示关联的 Issue 列表与状态

需求编号是这里的关键——v1 的标注只能带版本上下文，v2 能直接说清「这是 REQ-0275 的问题」，在需求系统里就地闭环。

### M6. 外部需求系统集成

抽象成仓库级 `mcp.json` + MCP 工具接口，Jira、禅道、GitHub Issues、GitLab Issues 或团队任务管理平台都由外部 MCP 服务负责适配：

```js
// MCP tools
{
  "requirements.search": { query, project, limit }, // 创建关联时的补全
  "requirements.get": { key, project },             // 拉标题、状态、负责人
  "requirements.comment": { key, body, project },   // 把原型链接写回需求单
  "requirements.test": { project }                  // 连接测试
}
```

**双向但不对称**：拉取是只读缓存（外部系统是权威）；写回只做一件事——**新基线定稿时在需求单里留一条评论，附原型直链**。不试图同步状态机，那是需求系统自己的事，两套状态机对齐是无底洞。

`mcp.json` 进 Git，记录服务 URL、Header 模板和能力映射；token 存本机钥匙串或环境变量不进 Git。无 token 时全部降级为纯本地需求，功能不残缺，只是少了自动补全和写回。

### M7. 上传路径与编辑

- 粘贴导入：`⌘V` 直接粘 HTML 源码 / `flowlark add --clipboard`
- URL 导入：`flowlark add https://...`（拒绝内网地址段防 SSRF）
- watch 提升为一等公民：常驻监听，自动归档为草稿
- 创建版本时**直接搜索关联需求**（走 provider 的 searchRequirements），而不是手抄编号

### M8. 通知

基线定稿、迭代冻结时触发 webhook（企微 / 钉钉 / Slack），消息带需求编号、版本号、变更条数、原型直链。

webhook 地址是团队共享配置进 Git；token 类敏感值走本地缓存。

### M9. 检索的需求维度

现有全库搜索加两个维度：按需求筛选、按迭代筛选。搜索结果可以直接跳到需求详情而不只是版本详情。

以及**影响面提示**：基于变更日志的「位置」字段，创建新版本时提示「你改的『订单列表-筛选区』，历史上关联过 REQ-0275、REQ-0301」，帮产品判断要不要把这些需求也关联上、帮研发判断回归范围。

## 五、架构演进

```
src/core/
  store.js          + 需求 / 迭代的读写；附件路径扩展
  rules.js          + 需求状态派生、迭代冻结规则
  requirements.js   ← 新增：需求实体与派生逻辑
  releases.js       ← 新增：迭代
  index.js          ← 新增：需求 → 版本反向索引（缓存，不进 Git）
  export.js         ← 新增：交付包生成
  migrate.js        ← 新增：schema 1 → 2
  permissions.js    ← 新增：Git 写权限探测与缓存
  integrations/
    provider.js     接口定义
    jira.js  zentao.js  github.js
  service.js        Hub 扩展；仍是 CLI 与 HTTP 的唯一事实来源
```

三条原则不变，v2 里更要守住：

**业务规则只写在 core。** 需求状态派生、迭代冻结判断这类逻辑绝不能在 CLI 和 Web 各写一遍。

**运行时零依赖。** 外部集成用内置 `fetch`，导出用内置 `zlib`。这条一旦破例，后面每个集成都会想拖个 SDK 进来。

**派生的东西不落库。** 需求状态、反向索引、外部元信息，全部可重算、可丢弃。

## 六、迁移方案

`schemaVersion: 1 → 2`，启动时自动执行，用户无感。

**迁移动作**：

1. 备份整个仓库到 `.flowlark/backup/v1-<时间戳>/`（不进 Git，迁移成功后保留一份供回退）
2. 扫描所有 `version.json` 的 `requirements` 数组，收集全部 `{code, title, url}`
3. 按 code 去重，为每个生成 `requirements/<code>/requirement.json`
   - 标题冲突时（同一编号在不同版本里写了不同标题）取**最新版本里的那个**，其余记进迁移报告
   - URL 解析出 provider 与 key，写进 `external`
4. 把各 `version.json` 的 `requirements` 改写为编号数组
5. `flowlark.json` 的 `schemaVersion` 改为 2
6. 输出迁移报告：生成了几个需求、有几处标题冲突、分别是什么

**安全性设计**：

- 迁移是**纯本地文件操作**，不触碰 Git。迁移后仓库处于「有未提交改动」状态，用户 review 完 `git diff` 再自己提交——这一步不能自动做，schema 迁移的提交应该由人确认。
- 迁移前检查工作区是否干净，不干净则拒绝并提示先提交，避免把迁移和业务改动混在一个 diff 里。
- 遇到任何无法处理的数据（比如 requirements 里有非对象项）**中止并回滚**，不做部分迁移。
- `schemaVersion: 2` 的仓库被 v1 版 Flowlark 打开时，v1 已有的版本检查会报「schema 版本过高」并提示升级——这条在 v1 里就写好了。

**回退**：`flowlark migrate --rollback` 从备份恢复。

## 七、CLI 新增面

```
需求
  req                      列出需求，按状态分组
  req <编号>               详情：关联版本、跨项目演进、变更聚合
  req new / link / unlink
  req spec / attach
  req sync                 从外部系统拉取元信息

迭代
  release                  列出迭代
  release new / add / rm
  release show <名称>      清单 + 未定稿告警
  release freeze
  release diff <A> <B>

导出
  export release <名称> -o <目录>
  export req <编号> -o <目录>

系统
  migrate                  手动触发迁移（正常情况下启动时自动）
  migrate --rollback
  whoami                   我在这个仓库是读还是写
```

现有命令的扩展：

- `add` 增加 `--req <编号>`（可重复），支持从外部系统搜索补全
- `search` 增加 `--req` 与 `--release` 筛选
- `status` 增加「有需求还没定稿」「有迭代该冻结了」的提示
- `diff` 增加 `--req <编号>`，看某个需求的全部变更

## 八、工作台新增视图

| 视图 | 回答什么 |
|---|---|
| 需求列表 | 现在有哪些需求，各自到哪一步了 |
| 需求详情 | 这个需求关联了哪些原型、演进过程、变更聚合、外部链接、相关 Issue |
| 迭代看板 | 这个迭代要交付什么、哪些还没定稿 |
| 交付包导出 | 选中迭代或需求，一键生成静态包 |
| 标注模式 | 在原型上框选提问，生成带需求上下文的 Issue |

导航主轴从「项目」变成**「项目 / 需求 / 迭代」三个并列入口**——同一批数据的三种切法，各自对应一类问题。

## 九、明确不做

| 不做 | 理由 |
|---|---|
| 镜像外部需求系统的完整状态机 | 两套状态机对齐是无底洞。Flowlark 只管原型侧的进展 |
| 需求的评审流程与审批链 | 那是需求系统的职责，Flowlark 不重造 |
| 自建账号体系 | 与本地形态冲突，权限交给 Git 平台 |
| 需求工时、排期、燃尽图 | 项目管理工具的领域 |
| 在线协同编辑原型 | 原型是单向产出的交付物，不是共创文档 |

## 十、软件层面的完成判据

| 模块 | 判据 |
|---|---|
| 需求实体 | 改一次需求标题，全库显示一致；能从需求反查到所有关联版本 |
| 派生状态 | 删掉 `.flowlark/cache/` 后所有需求状态能完全重算，结果一致 |
| 迭代 | `release show` 能指出哪些需求还停在草稿版本 |
| 交付包 | 导出的目录断网双击可用，包含全部原型、规格书、附件 |
| 权限 | 只读用户不可能产生推不上去的本地改动 |
| 迁移 | 任意 v1 仓库迁移后：需求数 = 去重后的编号数，且所有版本的关联关系一条不丢 |
| 集成 | 无 token 时全部功能可用，只是少了补全与写回 |
| 架构 | `dependencies` 仍为 `{}` |
