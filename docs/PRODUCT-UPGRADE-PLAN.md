# Flowlark 产品模块升级规划

> 基于当前 `v0.6.5` 代码与文档梳理。规划目标分两条线：一是补全已露出的未完善功能，二是升级真实团队可直接使用的新能力。

## 一、关键判断

Flowlark 已经从“本地原型版本库”扩展到“需求、迭代、交付、反馈、通知、Git 协作”的完整骨架。下一阶段不宜继续横向堆模块，而应把已有模块做深：减少产品经理上传和改稿成本，让研发、测试围绕需求和交付材料完成确认、反馈、验收。

成功标准：

- 产品经理能在一个工作台内完成上传、改稿、补变更、关联需求、设基线。
- 研发和测试能按需求、迭代、交付快照查看唯一可信材料。
- 反馈、审阅、通知和 Issue 状态能形成闭环，不再依赖群聊确认。
- 本地 + Git 的架构不变，不引入常驻团队服务器和自建账号体系。

## 二、现有模块盘点

| 模块 | 当前状态 | 主要差距 |
|---|---|---|
| 项目与版本 | 已支持项目、版本、基线、回滚、废弃、删除、恢复 | 版本创建后缺少“改稿”流程，变更日志仍偏手工维护 |
| 原型预览工作台 | 已支持预览、规格书、变更、需求、附件、历史 | 预览内定位、变更和反馈之间的联动还不够强 |
| 原型修改工作台 | 页面存在，但明确标注“尚未启用” | 这是最明确的未完成功能，应优先补齐 |
| 需求模块 | 已支持需求实体、列表、详情、派生状态、版本反查 | 缺需求级验收清单、外部需求系统同步、状态解释和批量维护 |
| 迭代模块 | 已支持迭代创建、版本加入、风险告警、导出包 | 缺冻结前检查流、迭代对比、研发验收视角 |
| 交付模块 | 已支持不可变快照、通知队列、Webhook 配置 | 缺交付包浏览体验、通知回执、交付验收记录 |
| 标注反馈 | 已支持反馈草稿、Markdown 导出、Issue 提交 | 缺反馈状态回流、需求聚合、重复反馈合并 |
| 搜索与视图 | 已支持需求、迭代、标签、状态、跨工作区搜索 | 缺高级筛选组合、结果批量操作、搜索解释 |
| Git 与权限 | 已支持 Git 助手、同步、冲突、只读探测、AI brief | 缺更细的安全审计和多远端/分支协作建议 |
| 安装、工作区、镜像、更新 | 已支持启动器、工作区注册/clone、镜像、更新检查 | 缺团队首次配置模板、镜像健康监控、升级回滚体验 |

## 三、升级主题

### 主题 A：补全未完善功能

#### A1. 原型修改工作台启用

问题：`SetupWizard.vue` 当前只是占位页，用户无法在产品内完成“局部改稿、生成新版、补变更记录”的闭环。

范围：

- 支持选择项目和基线版本作为改稿来源。
- 支持三种改稿输入：粘贴完整 HTML、上传替换 HTML、URL 导入。
- 支持生成新版前预览差异：标题、文件大小、外部依赖、关联需求、变更日志。
- 支持“沿用上一版需求”和“按变更位置推荐关联需求”。
- 支持改稿完成后直接进入新版本工作台。

验收：

- 产品经理从入口页开始，5 步内完成“选版本 → 替换原型 → 补变更 → 生成新版 → 设为基线”。
- 不允许绕过 `rules.requireChangelog` 和只读权限。

#### A2. 需求模块补全

问题：需求已经是一等实体，但还停留在“索引与查看”，缺少可执行的验收与维护能力。

范围：

- 需求详情增加验收清单：待补规格、待确认版本、待处理反馈、待交付附件。
- 增加需求级附件与需求规格编辑入口。
- 支持需求批量导入：CSV / Markdown 表格 / 粘贴多行文本。
- 支持需求状态解释：展示“为什么是设计中 / 已定稿 / 已交付”。
- 支持需求归档和恢复，避免历史需求污染活跃列表。

验收：

- 需求详情页能回答：该需求现在是否可以交付，阻塞项是什么，责任人是谁。

#### A3. 迭代模块补全

问题：迭代已有风险告警，但缺少从计划到冻结的操作流程。

范围：

- 新增迭代准备检查：未定稿、基线漂移、废弃版本、未确认审阅、缺规格书、缺变更日志。
- 增加迭代对比：本迭代相对上一迭代新增、移除、变更的需求和版本。
- 支持从需求列表批量加入迭代。
- 支持迭代状态：计划中、评审中、已冻结、已交付、已归档。
- 冻结前给出可执行修复入口，而不是只展示告警。

验收：

- 迭代冻结前，页面能一次列出全部阻塞项，并能跳转到对应修复位置。

#### A4. 反馈闭环补全

问题：反馈可以提交到 Issue，但 Flowlark 内缺少“反馈是否已处理”的回流。

范围：

- 反馈草稿、已提交 Issue、已关闭 Issue 统一聚合到需求和版本详情。
- 支持手动标记反馈状态：待处理、处理中、已解决、无需处理。
- Issue 平台可用时定时或手动刷新状态。
- 对同一需求、同一版本、相近区域的反馈提示可能重复。
- 交付快照创建时检查是否仍有未解决反馈。

验收：

- 研发提交反馈后，产品经理能在需求详情看到处理队列，并在交付前确认无遗留关键反馈。

#### A5. 交付模块补全

问题：快照已不可变，但交付后的验收和回执仍弱。

范围：

- 交付详情增加静态包入口、材料完整性检查、通知发送记录。
- 支持交付验收记录：验收人、结论、备注、时间。
- 支持交付包二次导出和校验：确认 HTML、规格、附件都存在。
- 通知队列增加失败原因、重试次数、最后响应。

验收：

- 一个交付快照能作为评审会和测试验收的唯一材料入口。

## 四、升级可用的新功能

### B1. AI 辅助变更日志与规格草稿

定位：本地优先，不内置模型账号。输出可复制给用户已有 AI 工具，或对接外部命令。

范围：

- 根据上一版和新版 HTML 的标题、文本节点、表单字段、按钮文案生成变更草稿。
- 根据需求、变更日志和规格书历史生成规格草稿。
- 生成 AI brief 时带上 Flowlark 数据约束：哪些文件可改，哪些不可改。
- 默认只生成草稿，必须由用户确认后写入。

边界：

- 不上传原型内容到第三方服务。
- 不承诺截图级 diff。

### B2. 外部需求系统集成

定位：把 Flowlark 的需求实体和团队已有需求池连接起来。

首批：

- Jira
- GitHub Issues
- GitLab Issues
- 禅道或 Gitee Issues，按目标团队实际工具二选一

范围：

- 搜索外部需求并创建本地映射。
- 拉取外部标题、状态、负责人到本地缓存。
- 新基线或交付冻结时回写一条评论，附原型链接和变更摘要。
- 外部系统不可用时降级为本地需求，不阻断主流程。

### B3. 交付包门户

定位：降低研发、测试、业务方查看门槛。

范围：

- 导出的静态包包含首页、需求索引、迭代索引、版本预览、规格书、变更日志、附件清单。
- 支持离线打开，不依赖 Flowlark 服务。
- 首页展示本次交付范围、阻塞项、验收状态、导出时间和校验摘要。

### B4. 工作区总览与团队模板

定位：让多仓库、多项目团队更容易落地。

范围：

- 工作区首页显示所有注册仓库的健康状态：缺失、可拉取、冲突、镜像异常、待更新。
- 支持团队配置模板：默认标签、通知模板、需求 URL 模板、规则开关。
- 支持导出和导入团队配置，敏感 token 仍只存本机。

### B5. 审计与治理

定位：让交付材料可追责。

范围：

- 增加审计视图：谁创建需求、谁切基线、谁确认审阅、谁冻结交付。
- 对高风险操作增加原因记录：关闭变更日志必填、删除版本、废弃基线关联版本。
- 支持按时间导出操作日志。

## 六、建议版本切分

### v0.7：补全工作流

目标：把已有骨架变成一条可执行的日常工作流。

- 原型修改工作台 MVP。
- 需求详情验收清单。
- 迭代冻结前检查。
- 交付详情完整性检查。
- 通知失败原因与重试详情。

### v0.8：协作闭环

目标：让反馈、审阅、交付不再靠群聊兜底。

- 反馈状态回流。
- 需求和版本聚合反馈。
- 迭代对比。
- 交付验收记录。
- 交付包门户。

### v0.9：团队化落地

目标：支持多仓库、多团队、存量迁移。

- 需求批量导入。
- 工作区健康总览。
- 团队配置模板。
- 镜像健康监控。
- 操作审计视图。

### v1.0：可正式推荐

目标：形成稳定边界和可宣传的产品闭环。

- 外部需求系统首批集成。
- AI 辅助草稿能力。
- 文档、安装、迁移、故障恢复收口。
- 桌面端和移动只读端回归验收。

## 七、模块级验收指标

| 模块 | 验收指标 |
|---|---|
| 原型修改工作台 | 从旧版本生成新版本不超过 5 步；只读和规则校验不可绕过 |
| 需求 | 每个需求详情能展示阻塞项、关联版本、反馈、交付状态 |
| 迭代 | 冻结前能列出全部阻塞项，且每个阻塞项有修复入口 |
| 反馈 | 反馈能按需求和版本聚合，能看到是否已解决 |
| 交付 | 快照材料可离线查看，通知和验收记录可追溯 |
| 搜索 | 常用视图可覆盖“本周待评审”“有反馈未处理”“基线已变化” |
| Git 权限 | 只读用户不能产生需要 push 的本地业务改动 |
| 分发 | 非技术成员能打开交付包或只读镜像，不依赖 CLI |

## 八、风险与取舍

| 风险 | 影响 | 建议 |
|---|---|---|
| 继续增加模块导致产品复杂 | 新用户学习成本上升 | 下一阶段优先做“工作流聚合”，少加独立入口 |
| 外部集成过早铺开 | 维护成本高 | 先选一个真实团队正在使用的平台 |
| AI 能力触碰原型内容隐私 | 推广受阻 | 默认本地生成 brief，由用户自己选择工具 |
| 交付包和镜像能力重叠 | 用户不知道该用哪个 | 交付包面向一次性交付，镜像面向长期浏览 |
| 状态字段过多 | 与 Git 派生原则冲突 | 能派生的状态继续派生，只有人工结论才落库 |

## 九、第一阶段实施建议

第一阶段只做 `v0.7`，不要同时开启外部需求系统和 AI。

实施顺序：

1. 原型修改工作台 MVP。
2. 需求详情验收清单。
3. 迭代冻结前检查流。
4. 交付详情完整性检查。
5. 通知失败详情。
6. 补测试和文档。

完成定义：

- `npm test` 通过。
- `npm run build:web` 通过。
- 新增工作流有 CLI 或 API 测试覆盖。
- 桌面端核心页面无明显溢出、重叠和空白占位。
