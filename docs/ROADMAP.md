# 产品升级路线图

> 目标形态：**产品经理上传与编辑原型，研发和测试浏览原型，文件管理走 Git。**
> 地基不变：仍然是本地软件 + Git 协作，不引入常驻服务器和账号体系。

---

## 一个推论，决定了后面所有设计

在「保持本地 + Git」这个约束下，**角色不需要 protohub 自己发明——它就是 Git 仓库权限的投影**：

| 角色 | Git 仓库权限 | 在 protohub 里意味着 |
|---|---|---|
| 产品经理 | write | `protohub sync` 能 push，是真正的写入方 |
| 研发 / 测试 | read | 能 clone、能 pull、push 会被拒 |

这个映射的好处是：**权限设施已经存在**。GitHub / GitLab / Gitee 的 collaborator 权限、公司的 LDAP 集成、离职时的权限回收，全都不用重做一遍。protohub 只要把这层权限**如实反映到界面上**。

坏处也很明确：**只读用户的反馈没有回路**。他推不上去，评论、标注、提问都送不回来。这是接下来要解决的核心问题，而不是靠加账号体系绕过去。

### 现状差距

| 能力 | 现在 | 差距 |
|---|---|---|
| 角色区分 | 靠「地点」近似：局域网只读、本机可写 | 产品经理出差用笔记本就改不了；研发在自己机器跑一份反而可写 |
| 只读用户的写入拦截 | 无。研发本地能改，push 时才失败 | 数据已经分叉了才报错，是最差的失败时机 |
| 反馈回路 | 无。只能另外开会说 | 研发看完原型的疑问，落不回 protohub |
| 上传 | CLI `add`；网页拖拽 | 产品每天做十几次的动作，路径还是偏长 |
| 检索 | 全库搜索、标签、累计变更 | 缺「按需求看」「按迭代看」这类聚合维度 |
| 流程衔接 | 需求号只存 URL 跳转 | 新基线不会通知任何人 |

## Now —— 让角色模型真正成立（1–2 周）

这一档只做一件事的三个面：**让「谁能写」这件事在正确的时机、以正确的方式发生**。

### N1. Git 权限感知的只读模式 ⭐ 最高优先级

**问题**：研发 clone 下来跑 protohub，界面上所有写操作按钮都在。他改了变更日志、切了基线，本地全部成功——直到 `protohub sync` 才发现 push 被拒。**此时本地已经产生了推不上去的提交，数据分叉了。**

**做法**：启动时探测远端写权限（`git push --dry-run`，或读取 `git ls-remote` 后尝试一次空推），结果缓存到 `.protohub/cache/`，界面据此进入只读模式：写按钮隐藏、CLI 写命令直接拒绝并说明原因。

**为什么是这个优先级**：这不是体验问题，是数据正确性问题。其余所有功能都建立在「谁能写」这件事是清楚的之上。

**取舍**：探测需要一次网络往返，所以缓存 + 手动刷新，别每次启动都卡几秒。探测失败时**默认可写**——离线办公不该被锁死，真推不上去时 Git 自己会拒。

**验收信号**：研发 clone 后打开工作台，第一眼就知道自己是只读的，且不可能做出推不上去的本地改动。

### N2. 标注 → Issue：把只读用户的反馈接回流程 ⭐

**问题**：研发看原型时的疑问（「这个按钮点了之后跳哪」「这个状态没有设计」）现在只能截图发群里，脱离版本上下文。

**做法**：在原型预览上框选区域 → 填写问题 → 一键生成 GitHub / GitLab Issue，自动带上：项目、版本号、当前基线、区域截图、原型直链、相关的变更日志条目。

**为什么走 Issue 而不是自建评论**：只读用户没有 push 权限，评论存不进仓库。而 Issue 系统本来就是给「没有写权限的人提意见」设计的，团队也已经在用它跟踪工作。自建一套评论只会多一个没人看的收件箱。

**取舍**：需要一个 token（用户自己在设置页填，存本地不进 Git）。没有 token 时降级为「复制成 Markdown」，用户自己贴到任何地方。

**验收信号**：研发的疑问从「群里一张截图」变成「带版本上下文的 Issue」，产品能直接从 Issue 跳回那一版原型。

### N3. 上传路径缩短到一步

**问题**：产品经理每天上传十几次，现在最短路径是 `protohub add 文件 -n 版本号 -t 标题`，还要想版本号和标题。

**做法**：
- **粘贴导入**：`protohub add --clipboard` / 网页 `⌘V` 直接粘贴 HTML 源码
- **URL 导入**：`protohub add https://...` 抓取 AI 工具给的分享链接
- **watch 提升为一等公民**：`protohub watch` 常驻，产品只管往文件夹里存，protohub 自动归档为草稿，攒够了再补变更日志转正
- 版本号与标题的推断更聪明：读 HTML 的 `<title>`、按上一版号递增

**为什么现在做**：这是产品经理接触这个工具的**唯一高频动作**。它慢一秒，一天就慢十几秒，一个月后人就不用了。

**取舍**：URL 导入要防 SSRF（拒绝内网地址段），且抓下来的页面仍按「单文件原型」处理，不做资源爬取——那是 `offline` 命令的事。

## Next —— 让日常真正顺手（1–2 个月）

### X1. 需求维度与迭代视图

现在的组织维度只有「项目 → 版本」。真实工作里还有两个维度：

- **按需求看**：REQ-0275 关联了哪些项目的哪几版？它的原型演进过程是什么？
- **按迭代看**：这个迭代要开发的原型有哪些？一次性打包给研发。

做法：新增 `protohub req <需求号>` 与「迭代」概念（本质是一组跨项目的版本引用，存成 `milestones/<名称>.json`）。

**为什么排在 Next**：项目数少于 5 个时用不上，超过 10 个就成了刚需。它是**规模问题**，不是从第一天就痛。

### X2. 移动端只读适配

研发和测试常在会议室、工位间用手机看原型。现在的工作台是桌面布局，手机上没法用。

只做只读路径：项目列表、版本时间线、原型全屏预览、规格书阅读、变更日志。写操作在手机上本来也不该做。

### X3. 新基线通知

产品切了基线，研发不知道。做法：切换基线时触发 webhook（企微/钉钉/Slack 机器人），消息里带版本号、变更条数、原型直链。

**取舍**：webhook 地址是团队共享配置，可以进 Git（`protohub.json`）；但 token 类的敏感值走本地缓存不进 Git。

### X4. 原型内锚点与深链

`protohub open ord v1.2#订单列表-筛选区` 直接定位到某个区域。前提是原型里有可锚定的元素——对 AI 生成的原型可以做启发式扫描（`id`、`data-*`、标题文本）。

配合 N2 的标注功能：Issue 里的链接点进去直接跳到出问题的区域。

### X5. 检索面板化

现有搜索是关键词命中列表。补上筛选维度：按标签、按状态、按时间范围、按创建人、按有无附件。搜索结果可保存成常用视图。

## Later —— 值得做但不急

### L1. 在线轻编辑

在工作台里直接改原型的文案、颜色、显隐。

**为什么排到最后**：原型是 AI 或设计工具生成的，主要改动路径是「重新生成再上传」，不是「在线精修」。在线编辑的真实需求只覆盖「改个错别字」这类长尾。而且它和 R4（基线不可变）有张力——只能作用于草稿版本。

先做的话，会是一个装饰性功能。

### L2. 设计工具导入

Figma / 即时设计 一键导入为原型版本。需要对接各家 API 且形态差异大，投入产出比要等前面的能力都站稳了再评估。

### L3. 跨仓库索引

大团队会有多个原型仓库。做一个本地索引，跨仓库搜索与导航。

### L4. 变更影响面提示

基于变更日志的「位置」字段，提示「这次改的区域，历史上关联过 REQ-0275、REQ-0301」，帮研发判断回归范围。

## 明确不做

| 不做 | 理由 |
|---|---|
| 自建账号与权限体系 | 与「保持本地」的地基冲突。权限交给 Git 平台，那是它擅长的事 |
| 常驻团队服务器 | 一旦有服务器，运维、备份、升级、可用性全都回来了。这个产品的价值有一半来自「没有这些」 |
| 实时协同编辑 | 原型不是共同创作的文档，是产品经理单向产出的交付物。冲突用 Git 解决就够 |
| 截图 / 源码级 diff | 成本高且没人看。变更日志 + 并排对比已经覆盖了真实需求 |
| 原型运行时数据 mock | 那是另一个产品 |

---

## 必须说清楚的代价

选择「保持本地」意味着**研发和测试要装 Node、clone 仓库、跑命令**。对不写代码的测试同学，这是真门槛，不能假装它不存在。

三条缓解路径，按投入排序：

1. **打包成免安装启动器**（Now 之后立刻做）：把 Node 运行时和已构建的工作台打进一个可执行文件，双击即用，内部自动 clone/pull。研发测试不需要知道 Node 是什么。
2. **产品经理开局域网**（已支持）：同一间办公室时最省事，同事浏览器直接访问，什么都不用装。代价是产品经理的机器得开着。
3. **只读镜像服务**（如果前两条都不够）：在一台常开机器上跑一个只拉不推的实例。这是往「加服务器」方向妥协半步，只在确实必要时再走。

第 1 条是这份规划里**唯一可能推翻「本地形态」判断的风险点**——如果打包后仍然有人装不上、跑不起来，那说明本地形态在这个团队不成立，应该重新评估第 2 个部署选项。建议在 Now 阶段结束后，找两个非技术同事实测一次，用结果说话。

## 阶段验收

| 阶段 | 一句话验收标准 |
|---|---|
| Now | 研发 clone 下来，不可能做出推不上去的改动；他的疑问能带着版本上下文进入团队的 Issue 系统 |
| Next | 产品经理不再需要在群里回答「哪一版是最新的」和「这个需求的原型在哪」 |
| Later | 视前面的实际使用情况再定，不预先承诺 |
