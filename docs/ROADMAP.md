# 产品升级路线图

> 目标形态：**产品经理上传与编辑原型，研发和测试浏览原型，文件管理走 Git。**
> 地基不变：仍然是本地软件 + Git 协作，不引入常驻服务器和账号体系。

---

## 一个推论，决定了后面所有设计

在「保持本地 + Git」这个约束下，**角色不需要 Flowlark 自己发明——它就是 Git 仓库权限的投影**：

| 角色 | Git 仓库权限 | 在 Flowlark 里意味着 |
|---|---|---|
| 产品经理 | write | `flowlark sync` 能 push，是真正的写入方 |
| 研发 / 测试 | read | 能 clone、能 pull、push 会被拒 |

这个映射的好处是：**权限设施已经存在**。GitHub / GitLab / Gitee 的 collaborator 权限、公司的 LDAP 集成、离职时的权限回收，全都不用重做一遍。Flowlark 只要把这层权限**如实反映到界面上**。

坏处也很明确：**只读用户的反馈没有回路**。他推不上去，评论、标注、提问都送不回来。这是接下来要解决的核心问题，而不是靠加账号体系绕过去。

### 现状差距

| 能力 | 现在 | 差距 |
|---|---|---|
| 角色区分 | 靠「地点」近似：局域网只读、本机可写 | 产品经理出差用笔记本就改不了；研发在自己机器跑一份反而可写 |
| 只读用户的写入拦截 | 无。研发本地能改，push 时才失败 | 数据已经分叉了才报错，是最差的失败时机 |
| 反馈回路 | 无。只能另外开会说 | 研发看完原型的疑问，落不回 flowlark |
| 上传 | CLI `add`；网页拖拽 | 产品每天做十几次的动作，路径还是偏长 |
| 检索 | 全库搜索、标签、累计变更 | 缺「按需求看」「按迭代看」这类聚合维度 |
| 流程衔接 | 需求号只存 URL 跳转 | 新基线不会通知任何人 |

## 版本总览

把原先的 Now / Next / Later 收敛成一个连续版本体系：当前版本定义为 `v0.1.0`，本轮升级目标为 `v0.2.0`，后续按小版本逐步补齐完整产品能力。

| 大版本 | 核心主题 | 一句话目标 |
|---|---|---|
| `v0.2.x` | 只读安全与基础体验 | Git 权限模型可用，首屏不卡，界面稳定 |
| `v0.3.x` | 反馈回路与上传提效 | 研发带上下文反馈，产品更快上传原型 |
| `v0.4.x` | 需求与迭代视图 | 从项目版本库升级成按需求 / 迭代组织原型 |
| `v0.5.x` | 团队交付与通知 | 新基线、交付、审阅状态进入团队协作流 |
| `v0.6.x` | 低门槛部署与分发 | 降低非技术成员安装、打开、查看门槛 |

## v0.2.x —— 只读安全与基础体验（当前大版本）

这一档先做一件事：**让「谁能写」这件事在正确的时机、以正确的方式发生**。本大版本只解决权限、性能和界面稳定，不同时引入 Issue 流、需求流和部署形态，避免一次升级改变过多基础假设。

**当前状态**：`v0.2.6` 已收口。Git 只读拦截、浅色主题、快速 Git 状态、状态缓存、主要写入口禁用、异常提示和发布文档已经作为当前大版本交付边界。

### v0.2.0 Git 权限感知只读模式

**问题**：研发 clone 下来跑 Flowlark，界面上所有写操作按钮都在。他改了变更日志、切了基线，本地全部成功，直到 `flowlark sync` 才发现 push 被拒。此时本地已经产生了推不上去的提交，数据分叉了。

**已落地**：
- `flowlark git permission` 查看本地缓存的远端写权限结果。
- `flowlark git permission --refresh` 主动执行远端写权限探测并刷新缓存。
- 明确探测到远端拒绝写入时，核心服务、HTTP API、CLI 写命令都会提前拒绝。
- 工作台顶部和 Git 面板会显示 Git 只读状态；只读状态下仍允许查询、预览、规格阅读等本地读路径。
- 探测失败或离线时默认暂按可写处理，避免离线办公被误锁。

**验收信号**：研发 clone 后打开工作台，第一眼就知道自己是只读的，且不可能做出推不上去的本地改动。

### v0.2.1 浅色主题与首屏性能修正

**范围**：
- 统一顶部、侧栏、搜索、项目列表为浅色主题，修复深色残留、搜索错位、菜单选中态难看等问题。
- 菜单选中态去掉左侧色条，只保留浅底、边框、文字权重和状态层次。
- 首屏加载不再被全量 Git 状态扫描拖慢，顶部 Git 状态和 Git 面板使用快速状态路径。
- 大仓库场景下避免扫描几十万无关文件，Git 状态刷新进入空闲或后台流程。

**验收信号**：进入项目页不应长时间卡在加载态；顶部和侧栏都保持浅色；搜索区域和菜单选中态无错位。

### v0.2.2 只读模式完整性

**范围**：
- 系统性梳理所有写入口：新增项目、上传版本、编辑元信息、设为基线、删除、同步、Git 写命令。
- 只读模式下隐藏或禁用写按钮，并给出统一提示文案。
- API 返回统一只读错误码，前端展示一致的只读说明。
- 增加只读 QA 矩阵：读权限用户、写权限用户、离线用户、权限探测失败用户。

**验收信号**：只读用户从 UI、API、CLI 三条路径都不能制造本地不可推送改动。

### v0.2.3 Git 性能与状态缓存

**范围**：
- Git 状态按仓库规模降级：优先读取项目相关路径，必要时再提供完整扫描按钮。
- 缓存最近一次 Git 状态，首屏直接展示缓存结果并后台刷新。
- Git 面板打开不阻塞页面交互。
- 对超大仓库给出明确提示：当前展示的是快速状态，完整状态需要手动刷新。

**验收信号**：包含大量非 Flowlark 文件的仓库仍能稳定打开项目页。

### v0.2.4 工作台布局稳定

**范围**：
- 重整预览、规格、变更、文档几个面板的响应式布局。
- 桌面端保证工具栏、预览区、详情区不互相挤压。
- 移动端先支持只读路径：项目列表、版本时间线、原型全屏预览、规格书阅读、变更日志。
- 空状态、错误状态、加载状态使用统一视觉语言。

**验收信号**：桌面和移动视口都不会出现内容重叠、按钮溢出、面板错位。

### v0.2.5 异常恢复与可理解错误

**范围**：
- 服务未启动、端口被占用、仓库未初始化、Git 不存在、网络中断时提供明确处理建议。
- 前端请求失败不无限加载，统一进入可恢复错误态。
- 补齐启动、刷新、权限探测、Git 快速状态的基础测试。

**验收信号**：异常不再表现为“加载半天”，用户能看到原因和下一步。

### v0.2.6 发布候选与文档收口

**范围**：
- 更新用户安装、启动、只读模式、Git 权限、常见问题文档。
- 固化 v0.2.x 的验收清单和回归清单。
- 形成 `v0.2.0` 到 `v0.2.6` 的 release notes。

**验收信号**：v0.2.x 可作为一个稳定小版本系列交付给真实团队试用。

## v0.3.x —— 反馈回路与上传提效

这一档解决两个高频痛点：研发看完原型后如何反馈，产品经理如何更快上传原型。

| 版本 | 升级要点 | 验收信号 |
|---|---|---|
| `v0.3.0` | 原型预览标注反馈：框选区域、填写问题、绑定项目版本和基线 | 研发反馈天然带版本上下文 |
| `v0.3.1` | 无 token 降级为 Markdown 反馈导出 | 没接 Issue 平台也能复制到任意协作工具 |
| `v0.3.2` | GitHub Issue 集成 | 标注可一键生成带截图、链接、版本信息的 Issue |
| `v0.3.3` | GitLab / Gitee Issue 集成 | 国内和企业自建 Git 平台可用 |
| `v0.3.4` | 拖拽 / 粘贴 HTML 上传，自动读取 `<title>` | 上传不再依赖完整 CLI 参数 |
| `v0.3.5` | URL 导入原型，带 SSRF 防护 | AI 工具分享链接可以被安全归档 |
| `v0.3.6` | `flowlark watch` 产品化：草稿箱、自动归档、补日志转正 | 产品只管保存文件，Flowlark 自动收集 |

**边界**：不自建评论系统。只读用户没有 push 权限，评论存不进仓库；反馈应进入团队已有 Issue 或导出为 Markdown。

## v0.4.x —— 需求与迭代视图

这一档把 Flowlark 从“项目版本库”升级为“需求和迭代里的原型资产库”。

| 版本 | 升级要点 | 验收信号 |
|---|---|---|
| `v0.4.0` | 新增需求视图：按需求号聚合跨项目原型版本 | 能回答“REQ-0275 的原型在哪” |
| `v0.4.1` | 需求详情页：版本演进、关联变更、反馈列表 | 一个需求的设计过程可追溯 |
| `v0.4.2` | `milestones/<名称>.json` 作为迭代数据结构 | 迭代可以引用多个项目的多个版本 |
| `v0.4.3` | 迭代视图：本迭代原型、基线、状态 | 研发能按迭代查看要开发的原型 |
| `v0.4.4` | 迭代交付包：导出原型清单、变更摘要、链接集合 | 交付不再靠群里逐条发链接 |
| `v0.4.5` | 搜索面板化：标签、状态、时间、需求号、附件筛选 | 搜索从关键词列表变成可筛选工作台 |
| `v0.4.6` | 保存常用视图 | 团队可复用“本周待评审”“有反馈未处理”等视图 |

**边界**：不做完整需求管理系统。需求和迭代只作为原型资产的组织维度存在。

## v0.6.x —— 低门槛部署与分发

这一档降低非技术成员的使用门槛，验证“本地软件 + Git 协作”是否能覆盖真实团队。

| 版本 | 升级要点 | 验收信号 |
|---|---|---|
| `v0.6.0` | 免安装启动器：内置运行时，双击启动 | 测试同学不需要理解 Node 和 CLI |
| `v0.6.1` | 首次使用向导：选择仓库、自动 clone / pull、打开只读视图 | 新成员可以自己完成初始化 |
| `v0.6.2` | 自动更新和版本检查 | 团队不靠手动替换文件升级 |
| `v0.6.3` | 只读镜像模式评估：一台常开机器只拉不推 | 对完全非技术用户提供浏览入口 |
| `v0.6.4` | 跨仓库本地索引 | 多个原型仓库可统一搜索和导航 |
| `v0.6.5` | 安装、升级、故障排查文档闭环 | 非开发角色遇到问题能按文档恢复 |

**边界**：只读镜像服务是对“无常驻服务器”原则的半步妥协，只在启动器仍不能覆盖目标团队时启用。

## 当前收口顺序

1. `v0.2.x` 已收口为 `v0.2.6`：浅色主题、首屏性能、样式错位、加载异常、只读完整性和 Git 状态缓存。
2. 下一阶段进入 `v0.3.x`：先做 Markdown 反馈导出，再接 GitHub / GitLab / Gitee Issue。
3. `v0.4.x` 以后只在真实项目数量和团队规模上来后推进，避免过早复杂化。

---

## 明确不做

| 不做 | 理由 |
|---|---|
| 自建账号与权限体系 | 与「保持本地」的地基冲突。权限交给 Git 平台，那是它擅长的事 |
| 常驻团队服务器 | 一旦有服务器，运维、备份、升级、可用性全都回来了。这个产品的价值有一半来自「没有这些」 |
| 实时协同编辑 | 原型不是共同创作的文档，是产品经理单向产出的交付物。冲突用 Git 解决就够 |
| 截图 / 源码级 diff | 成本高且没人看。变更日志 + 并排对比已经覆盖了真实需求 |
| 原型运行时数据 mock | 那是另一个产品 |

---

## 必须说清楚的代价

选择「保持本地」意味着**研发和测试要装 Node、clone 仓库、跑命令**。对不写代码的测试同学，这是真门槛，不能假装它不存在。

三条缓解路径，按投入排序：

1. **打包成免安装启动器**（`v0.6.x` 重点验证）：把 Node 运行时和已构建的工作台打进一个可执行文件，双击即用，内部自动 clone/pull。研发测试不需要知道 Node 是什么。
2. **产品经理开局域网**（已支持）：同一间办公室时最省事，同事浏览器直接访问，什么都不用装。代价是产品经理的机器得开着。
3. **只读镜像服务**（如果前两条都不够）：在一台常开机器上跑一个只拉不推的实例。这是往「加服务器」方向妥协半步，只在确实必要时再走。

第 1 条是这份规划里**唯一可能推翻「本地形态」判断的风险点**——如果打包后仍然有人装不上、跑不起来，那说明本地形态在这个团队不成立，应该重新评估第 2 个部署选项。建议在 `v0.6.x` 启动器方案完成后，找两个非技术同事实测一次，用结果说话。

## 阶段验收

| 阶段 | 一句话验收标准 |
|---|---|
| `v0.2.x` | 研发 clone 下来，不可能做出推不上去的改动；项目页不被 Git 状态拖慢 |
| `v0.3.x` | 研发反馈能带着版本上下文进入 Issue / Markdown；产品上传路径明显缩短 |
| `v0.4.x` | 产品经理不再需要在群里回答「哪一版是最新的」和「这个需求的原型在哪」 |
| `v0.5.x` | 新基线、审阅状态、交付材料能主动进入团队已有协作流 |
| `v0.6.x` | 非技术成员可以低门槛打开只读视图，并能按文档完成安装、升级和故障恢复 |
