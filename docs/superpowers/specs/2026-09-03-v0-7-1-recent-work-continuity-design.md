# Flowlark 小版本升级规划：最近工作续接体验优化

## 1. 版本定位

- 暂定规划号：`v0.7.1`
- 版本主题：最近工作续接体验优化
- 规划周期：4 周
- 优化链路：个人工作台 → 项目列表 → 项目版本页 → 版本工作台

`v0.7.1` 是产品规划号，不直接等同于当前仓库的发布标签。仓库目前没有 `v0.7.0` Git 标签，且 `main` 已包含 `CHANGELOG.md` 中尚未发布的能力。进入正式发版前，必须先确认当前 `main` 是否作为本轮验收基线，并冻结准确的发布提交范围。本轮规划自身不增加业务功能。

## 2. 背景与问题

当前个人工作台以项目、需求、迭代和交付数量为主，并提供固定的流程入口。它能回答“系统里有什么”，但不能直接回答“我最近改了什么、现在从哪里继续”。用户仍需先进入项目列表，再判断最近项目和目标版本，工作上下文在页面间断开。

项目列表、项目版本页和版本工作台已经具备最新版本、基线、评审状态、更新时间和直接路由等基础能力。本轮不横向增加模块，而是重排这些已有信息，形成一条连续的工作续接路径。

## 3. 目标与成功标准

### 3.1 产品目标

用户打开 Flowlark 后，可以快速识别最近修改的项目或版本，并沿同一条上下文链路继续处理。

### 3.2 核心成功标准

1. 用户打开个人工作台后，10 秒内可以识别最近修改的内容。
2. 从个人工作台最多点击一次即可进入对应版本工作台；没有有效目标版本时进入项目版本页。
3. 个人工作台、项目列表、项目版本页和版本工作台使用一致的时间、状态和操作层级。
4. 1440×900 桌面视口和 390×844 移动视口下，不出现横向溢出、文字遮挡、按钮截断或返回路径丢失。
5. 操作日志或健康状态局部加载失败时，最近工作主列表仍可使用。

### 3.3 优先级

若效率目标与视觉完善发生工期冲突，优先保证“10 秒识别、一次点击续接”，再收口视觉一致性。

## 4. 范围边界

### 4.1 范围内

- 重构个人工作台的信息优先级。
- 优化项目列表的最近更新识别和主操作。
- 优化项目版本页的版本定位、基线关系和下一步动作。
- 优化版本工作台的项目与版本上下文、返回路径和状态表达。
- 统一四页的标题、时间、状态、主次操作和响应式表现。
- 复用现有项目摘要、版本摘要、操作日志、健康状态和路由。
- 为前端聚合、排序、降级和路由规则补充单元测试。

### 4.2 明确不做

- 不新增业务模块或一级导航。
- 不新增收藏、置顶、访问历史或智能推荐。
- 不记录用户浏览行为。
- 不修改后端数据模型、Git 工作流、权限机制和仓库存储格式。
- 不扩展需求、迭代和交付链路。
- 不进行全站视觉重构。
- 不顺带重构无关组件、命名或样式。

## 5. 方案选择

采用“连续工作流优化”方案：围绕“最近修改 → 找到项目 → 定位版本 → 继续处理”统一四个页面。

未采用的方案：

- 仅调整工作台：改动小，但进入项目后仍会出现上下文断层。
- 全面视觉翻新：一致性更强，但容易扩大成前端重构，挤压工作流验证时间。

## 6. 页面设计

### 6.1 个人工作台

“最近工作”成为首屏主内容，现有四个业务数量指标降为辅助信息，不再占据最高视觉层级。

每条最近工作展示：

- 项目名称与项目代码。
- 目标版本号与标题；没有版本时显示“暂无版本”。
- 最近更新时间。
- 当前基线状态。
- 最近一次可用操作摘要。
- 单一主操作“继续处理”。

默认展示 8 个不同项目。点击整行或“继续处理”执行同一个导航动作：目标版本有效时直接进入版本工作台，否则进入项目版本页。

工作区状态保留，但降低视觉权重。现有“确认项目基线、核对需求关联、检查迭代风险、准备评审交付”等固定入口不再作为首屏主体；相关能力仍可通过现有一级导航访问。

### 6.2 项目列表

项目列表默认突出最近更新的活跃项目。每个项目应让用户快速判断：

- 最新可用版本及其标题。
- 当前基线。
- 最新版本是否与基线一致。
- 最近更新时间。
- 下一步进入项目还是直接处理最新版本。

每个项目只保留一个突出的主操作“继续”。存在有效最新版本时直接进入版本工作台；没有版本时进入项目版本页。编辑项目等操作保留在次级菜单中。

搜索和归档筛选继续沿用现有能力，不新增筛选维度。

### 6.3 项目版本页

页面顶部集中展示：

- 项目名称、代码和说明。
- 当前基线。
- 最新可用版本。
- 最新版本与基线的关系。
- 最近更新时间。
- “继续处理最新版本”主操作。

版本列表继续按时间倒序。列表强化版本号、标题、更新时间、评审状态和基线状态的扫描层级，每行只突出“打开版本”。比较、回滚、废弃等已有操作保持为次级操作，不改变原有权限和确认规则。

筛选条件、选择状态、基线规划摘要和现有详情能力保持不变。

### 6.4 版本工作台

保留原型预览、版本文档、规格、变更、反馈、编辑、比较、下载和设基线等现有能力，只优化上下文表达：

- 明确显示“项目 → 当前版本”的位置关系。
- 固定提供返回项目版本页的入口。
- 标题区同时展示版本号、基线关系、评审状态和更新时间。
- 从工作台或项目列表进入后不增加中转页面。
- 桌面端维持现有分栏效率，移动端维持预览与文档单列切换。

不得借本轮调整改变原型编辑、反馈、审阅、比较、下载或基线切换行为。

### 6.5 跨页一致性

- 时间统一沿用现有 `YYYY-MM-DD HH:mm` 格式，不在本轮引入第二套相对时间口径。
- 基线、版本和评审状态复用现有状态语义，不创建第二套状态名称。
- 每页同一时刻只突出一个与续接路径有关的主要操作。
- 返回、继续、编辑、更多和危险操作使用稳定的视觉层级。
- 状态不能只靠颜色表达，必须同时显示文字。

## 7. 数据与排序规则

### 7.1 数据来源

- `GET /api/projects`：项目、项目更新时间、最新非废弃版本、基线和版本数量。
- `GET /api/oplog`：最近项目操作、关联版本、操作摘要和操作时间。
- `GET /api/health`：工作区、写权限和运行状态。
- `GET /api/versions/:slug/:no`：按需校验最近日志关联的目标版本是否仍可打开。
- 项目版本页与版本工作台继续使用各自现有接口。

本轮不增加新的后端聚合接口。

### 7.2 最近工作生成规则

1. 以项目为聚合单位，每个项目最多生成一条记录。
2. 默认排除已归档项目。
3. 最新目标版本取项目摘要中的最新非废弃版本。
4. 项目活跃时间取以下时间的最大值：
   - 项目 `updatedAt`；
   - 最新版本 `updatedAt`；
   - 该项目最新操作日志 `at`。
5. 最近操作摘要取该项目最新一条有效日志的 `detail`。
6. 按活跃时间倒序排列；时间相同时按项目名称稳定排序。
7. 最多显示 8 条。
8. 对进入前 8 条结果、且最新日志带版本号的项目，并行调用现有版本详情接口校验目标。
9. 日志目标仍存在且未废弃时，该版本优先作为导航目标；校验失败、目标已废弃或日志没有版本号时，使用项目最新非废弃版本。
10. 没有有效版本时进入项目版本页，不生成失效直链。

### 7.3 纯函数边界

前端新增独立的最近工作模型函数，输入为项目数组和操作日志数组，输出为稳定排序后的工作项。该函数不读取浏览器状态、不发起请求、不修改源数据，供个人工作台和项目列表复用。

## 8. 数据流与错误处理

个人工作台先并行读取项目、操作日志和健康状态，再对前 8 条候选记录中带版本号的日志目标并行执行版本详情校验。项目数据是最近工作列表的最低可用依赖，操作日志、目标校验和健康状态是可降级依赖。

降级规则：

- 操作日志加载失败：仅使用项目和版本更新时间排序，不阻断页面。
- 健康状态加载失败：只影响工作区状态区域，不影响最近工作列表。
- 单条日志目标校验失败或目标无效：回退到项目最新非废弃版本或项目版本页。
- 单个字段缺失：展示明确占位，不隐藏整条有效记录。
- 项目数据加载失败：展示可重试错误态，不用旧指标伪装成功。
- 全部项目为空：沿用现有空状态，引导进入项目页。
- 只读模式：正常显示最近工作和导航，仅禁用已有写操作。

请求完成后只更新当前页面仍有效的状态，避免路由切换或刷新时旧请求覆盖新结果。

## 9. 四周实施节奏

### 第 1 周：规则与个人工作台

- 固化最近工作数据结构、排序和降级规则。
- 编写纯函数单元测试。
- 将个人工作台主内容调整为最近工作。
- 保留并降级展示现有指标和工作区状态。
- 完成桌面端首轮走查。

阶段验收：不同项目、重复日志、无版本项目、废弃版本和日志失败场景均产生稳定结果；工作台能一次点击进入正确目标。

### 第 2 周：项目列表

- 复用最近工作排序口径。
- 优化最新版本、基线关系、更新时间和主操作层级。
- 保持搜索、归档筛选和项目编辑行为不变。
- 补充项目列表模型与导航测试。

阶段验收：用户从工作台或项目列表进入同一项目时，看到的最新版本与续接目标一致。

### 第 3 周：项目版本页与版本工作台

- 收口项目版本页顶部摘要和版本列表扫描层级。
- 增加“继续处理最新版本”的明确主操作。
- 统一版本工作台的项目、版本、基线、评审和更新时间上下文。
- 保持筛选、比较、编辑、反馈、下载和基线操作不变。

阶段验收：四页之间的目标版本、基线状态和返回路径一致；现有版本操作无回归。

### 第 4 周：响应式、回归与发布准备

- 完成 1440×900 与 390×844 视口走查。
- 修复溢出、遮挡、截断、跳版和触控目标问题。
- 执行前端构建、相关单元测试和全量测试。
- 完成 3 个核心任务的人工可用性验收。
- 更新变更日志和发布说明，并确认实际发布边界。

阶段验收：自动化验证通过，核心任务人工验收通过，未将当前 `main` 中其他未发布能力误归入本轮优化范围。

## 10. 测试与验收

### 10.1 模型测试

至少覆盖：

- 项目、版本和日志时间取最大值。
- 同一项目多条日志去重。
- 时间相同的稳定排序。
- 已归档项目排除。
- 已废弃或不存在的日志目标降级。
- 无版本项目进入项目版本页。
- 日志为空或加载失败时仍按项目数据生成结果。
- 日志目标有效、已废弃、不存在或校验失败时选择正确的降级路由。
- 最多返回 8 条。

### 10.2 页面与路由测试

- 工作台最近工作点击进入正确版本。
- 项目列表“继续”与工作台目标一致。
- 项目版本页主操作进入最新有效版本。
- 版本工作台返回正确项目版本页。
- 只读状态下导航可用、写操作仍受现有规则限制。
- 部分接口失败时显示局部提示，主列表保持可用。

### 10.3 视觉与响应式验收

检查个人工作台、项目列表、项目版本页和版本工作台：

- 1440×900 桌面视口。
- 390×844 移动视口。
- 长项目名、长版本标题、无基线、无版本、只读和错误状态。
- 无横向溢出、文字遮挡、按钮截断、状态仅靠颜色表达或卡片嵌套膨胀。

### 10.4 核心任务人工验收

任务一：从工作台找到最近修改的版本并继续处理。

- 目标：10 秒内识别，最多点击一次进入版本工作台。

任务二：从项目列表判断最新版本与基线是否一致。

- 目标：不进入详情即可完成判断，并能直接继续处理最新版本。

任务三：从版本工作台返回项目并切换另一版本。

- 目标：返回路径明确，切换后项目和版本上下文不混淆。

### 10.5 工程验证

- 相关前端模型和页面测试通过。
- `npm run build:web` 通过。
- `npm test` 通过。
- 浏览器控制台无新增错误。

## 11. 风险与控制

| 风险 | 影响 | 控制方式 |
|---|---|---|
| 操作日志包含大量同项目记录 | 首屏被单一项目占满 | 按项目去重，每个项目只保留一条 |
| 项目更新时间与版本更新时间语义不同 | 最近排序不符合直觉 | 统一取项目、版本和日志的最大时间，并通过测试锁定 |
| 日志指向已删除或废弃版本 | 产生失效入口 | 使用现有版本详情接口校验前 8 条目标，失败时回退到最新有效版本或项目页 |
| 日志目标校验增加本地请求 | 首屏加载出现抖动 | 只校验最终候选项、并行请求、完成校验后一次性展示稳定列表 |
| 四页同时调整导致范围扩大 | 一个月内无法完成 | 只调整信息层级和续接路径，不改变业务行为 |
| 视觉优化演变成组件库重构 | 引入无关回归 | 复用现有组件和 token，只抽取必要的纯模型或轻量展示单元 |
| 当前 `main` 混有未发布能力 | 小版本实际包含新功能 | 发版前冻结并审查发布提交范围，规划号与发布标签分开确认 |

## 13. 完成定义

同时满足以下条件才视为本轮完成：

1. 范围内四页全部完成并通过对应测试。
2. 三个核心人工任务达到目标。
3. 桌面端和移动端视觉验收通过。
4. 未改变范围外的业务功能、数据模型、Git 行为和权限规则。
5. 自动化测试与前端构建通过。
6. 实际发布边界已确认，版本号与变更日志一致。
