# 草稿箱与回收站任务队列化升级设计

## 背景

Flowlark 当前的“草稿箱”实际是 watch 导入记录列表：新 HTML 被收集后会立即尝试归档为版本，成功项和失败项都会继续保留。页面只能打开已归档版本或逐条重试失败项，缺少筛选、批量处理和历史清理能力。

“回收站”当前只保存被删除的版本，支持按项目和版本号逐条恢复。列表没有恢复资格提示，也不能区分同一版本号多次进入回收站形成的不同删除记录。批量恢复时，版本号冲突会迫使用户逐项发现和处理。

本次升级不统一版本草稿、AI 草稿和反馈草稿的数据模型，而是在现有 watch inbox 与 version trash 边界内，将两个页面升级为高效、可恢复的任务队列。

## 目标

- 让用户快速定位需要处理的草稿或回收站条目。
- 通过一次批量动作完成多个失败重试、历史记录清理或版本恢复。
- 允许批量操作部分成功，失败项可继续处理。
- 在执行恢复前显示冲突和数据异常，减少无效点击。
- 保持现有 CLI、单项接口和磁盘存储兼容。

## 非目标

- 不把版本草稿、AI 草稿或反馈草稿合并进 watch 草稿箱。
- 不改变 `.flowlark/cache/watch/inbox.json` 和 `.flowlark/trash/` 的文件布局。
- 不增加自动过期、永久删除、容量治理或服务端分页。
- 不删除 watch 的原始 HTML，也不因清理 watch 记录而删除已生成版本。
- 不重构无关页面、命令或通用工作流框架。

## 成功标准

- 用户最多两次操作即可筛出某项目的失败草稿。
- 用户可以一次选择并重试多个失败项。
- 用户可以批量清理已归档 watch 记录，且不影响版本和源文件。
- 用户可以一次恢复多个回收站条目；一个条目冲突不会阻断其他条目。
- 批量操作结束后显示成功、跳过和失败的逐项结果。
- 刷新页面或分享 URL 后，当前筛选上下文保持不变。
- 只读模式允许浏览，但没有可触发的写操作。
- 现有 watch、trash、restore 和 CLI 行为无回归。

## 设计原则

1. **队列优先于历史。** 默认把需要动作的条目放在最前，成功历史退居次级视图。
2. **批量由单项能力组合。** 不新建批量业务接口；前端以有限并发调用单项接口并汇总结果。
3. **部分失败可继续。** 单项失败不回滚已经成功的条目，也不终止剩余条目。
4. **服务端最终校验。** 前端状态只用于提前提示，服务端在每次写操作时重新校验。
5. **破坏性边界写清楚。** “清理记录”与“删除版本”必须使用不同文案并明确影响范围。

## 升级路线

### Release 1：快速定位

草稿箱和回收站先统一筛选、计数和 URL 状态，不增加写能力。

- 草稿箱增加待处理、归档失败、已归档三个计数。
- 草稿箱支持项目、状态、标题或文件名关键词、收集时间筛选。
- 回收站支持项目、版本号关键词和删除时间筛选。
- 草稿箱默认展示待处理视图，失败项排在 pending 项之前；已归档记录进入独立视图。
- 筛选条件写入 URL；从项目页进入时自动应用 `project=<slug>`。
- 桌面端使用表格，移动端保持紧凑列表；Release 2 和 Release 3 交付对应批量动作时再启用复选框，避免 Release 1 出现无动作的选择状态。

### Release 2：草稿批量处理

- 支持选择多个失败项并批量重试。
- 支持选择多个已归档项并清理 watch 记录。
- 混合选择时分别显示“重试失败项（N）”和“清理已归档记录（N）”，不要求用户先手动拆分选择。
- 清理前确认文案明确说明：只移除草稿箱记录，不删除已创建版本或源 HTML。
- 结果面板展示成功与失败明细，并提供“仅选择失败项”。

### Release 3：回收站批量恢复

- 每条删除记录获得稳定的 API `id`，同一项目和版本号的多次删除可被准确区分。
- 回收站列表展示可恢复、版本号已占用、项目不存在、数据不完整四类状态。
- 批量恢复前跳过当前不可恢复项，继续执行其余条目。
- 结果面板展示成功、跳过和失败明细，支持复制明细和仅重新选择失败项。

## 草稿箱交互

页面头部显示待处理、归档失败和已归档数量。默认视图只包含 pending 与 failed 条目，按“失败优先、时间倒序”排列。已归档视图按时间倒序展示历史记录。

筛选栏包含项目、状态、关键词和时间范围。项目和状态使用枚举控件，关键词匹配标题与文件名。筛选结果与当前选择分离：切换筛选不会删除已选条目，但批量栏必须说明当前选择中各动作可处理的数量。

单项动作保持现有语义：

- `archived`：打开生成的版本。
- `failed`：重新归档。
- `pending`：只展示处理中状态，不允许清理或重试。

新增的“清理记录”只允许作用于 `archived`。服务端拒绝清理 pending 或 failed 条目，避免丢失处理中状态或失败诊断。

## 回收站交互

列表字段包括项目、版本号、删除时间、删除人和恢复状态。恢复状态由当前仓库状态动态计算：

| 状态 | 条件 | 交互 |
|---|---|---|
| 可恢复 | 项目存在、目标版本号未占用、必要文件存在 | 允许选择和恢复 |
| 版本号已占用 | 当前项目已有同号版本 | 禁止恢复，提示先处理现有版本 |
| 项目不存在 | 项目元数据已不存在 | 禁止恢复，提示先恢复或重建项目 |
| 数据不完整 | 回收记录缺少版本 JSON 或其他必要元数据 | 禁止恢复，展示缺失原因 |

混合选择时，“批量恢复”只执行可恢复条目，其余条目计入跳过结果。单项恢复保留确认步骤；批量恢复使用一次总确认，避免逐条弹窗。

## API 设计

### 清理已归档 watch 记录

```http
DELETE /api/watch/inbox/:id
```

服务端规则：

- ID 必须通过现有 UUID 校验。
- 记录必须存在且状态为 `archived`。
- 删除只修改 `inbox.json`，不触碰 `sourcePath` 和已生成版本。
- 只读仓库拒绝执行。

响应返回被移除的 `id`、`project`、`versionNo` 和 `status`，便于前端准确更新列表。

### 回收站列表

```http
GET /api/trash?project=<slug>
```

现有元信息继续返回，并增加：

```json
{
  "id": "<opaque-trash-entry-id>",
  "canRestore": true,
  "blockedReason": null
}
```

`id` 由服务端根据回收站项目目录和条目目录生成不透明标识。API 不再要求前端依赖绝对磁盘路径；现有 `dir` 字段可在兼容期保留，但新页面不得使用。

### 按删除记录恢复

```http
POST /api/trash/:id/restore
```

服务端通过 `id` 定位唯一删除记录，重新检查项目、版本号占用和文件完整性后执行现有恢复流程。旧的 `POST /api/versions/:slug/:no/restore` 继续保留，供 CLI 和已有页面调用。

## Core 边界

`watch-inbox.js` 增加删除单条已归档记录的能力。读写仍复用现有原子临时文件替换，避免并发写入留下半个 JSON 文件。

`store.js` 继续负责枚举回收站目录和移动文件，不包含页面状态。回收站 ID 的解析必须校验路径片段，解析结果必须保持在 `.flowlark/trash/` 内，不能接受绝对路径或 `..`。

`service.js` 负责恢复资格判断、只读权限、业务错误映射和操作日志。列表资格是提示，恢复方法必须再次执行相同校验，防止加载列表后仓库状态发生变化。

## 前端模型与批量执行

页面逻辑拆为可单测的纯函数：

- 计数与筛选。
- 状态排序。
- 从 URL 解析和序列化筛选条件。
- 根据选择计算各动作的 eligible 数量。
- 将 `Promise.allSettled` 结果归并为成功、跳过和失败。

批量请求最多并发 3 个，避免大量本地文件写入同时发生。单项成功后立即从当前待处理集合移除；失败项保留选择。操作结束后重新加载服务端列表，页面不以本地乐观状态作为最终事实。

## 权限与错误处理

- 只读仓库：隐藏或禁用所有写操作，但保留筛选、复制和打开版本能力。
- 状态过期：服务端返回明确业务错误，前端归入“跳过”或“失败”并刷新列表。
- 网络中断：未确认成功的条目保持选择，允许用户再次执行。
- 版本号冲突：归入“跳过”，不中断其他恢复。
- 非法或过期回收站 ID：返回未找到，不泄露本地绝对路径。
- 部分成功：不得显示整批失败，也不得回滚成功条目。

## 无障碍与文案

- 状态不能只依赖颜色，必须同时显示文字标签。
- 表格复选框和批量动作提供可读的 `aria-label`。
- 批量执行期间使用可感知的加载状态，结果摘要通过消息区域播报。
- “清理记录”“删除版本”“恢复版本”使用不同动词，避免用户误判影响范围。
- 确认弹窗只用于具有数据影响的动作；筛选、重试失败项选择和复制明细不弹窗。

## 测试策略

### Core 与 API

- 已归档 watch 记录可以删除，pending 和 failed 记录被拒绝。
- 删除 watch 记录不影响源 HTML 和已生成版本。
- 回收站 ID 能区分同版本号的多次删除记录。
- ID 路径穿越、非法 ID 和已不存在记录被拒绝。
- 恢复资格覆盖可恢复、同号占用、项目不存在和数据不完整。
- 列表后状态变化时，恢复接口重新校验。
- 只读仓库拒绝清理和恢复。

### 页面模型与 UI

- 计数、组合筛选、失败优先排序和 URL 往返一致。
- 混合选择正确计算各批量动作数量。
- 部分成功结果正确归入成功、跳过和失败。
- 批量完成后成功项消失、失败项保持选择。
- 移动端列表与桌面表格暴露相同动作。

### 回归

- 运行现有 watch、trash、restore、CLI 和 server 测试。
- 运行新增页面模型测试与前端构建。
- 手工验证只读模式、网络失败和同号冲突。

## 估算与发布

按一名熟悉代码库的全栈工程师估算：

| 发布 | 估算 | 风险 |
|---|---:|---|
| Release 1：快速定位 | 2–3 工程日 | 低，主要是纯展示和 URL 状态 |
| Release 2：草稿批量处理 | 2–3 工程日 | 中，新增记录清理与部分失败反馈 |
| Release 3：回收站批量恢复 | 3–4 工程日 | 中，需处理稳定 ID 和状态竞争 |

每个 Release 可以独立发布和回滚。Release 1 不依赖项目原型管理升级的其他部分，只复用 `project` 查询参数约定。

## 风险与后续边界

- 同一版本多次删除会产生重复记录，因此批量恢复必须依赖稳定条目 ID，不能继续只使用项目和版本号。
- 页面加载后仓库可能被 CLI 或其他浏览器会话修改，因此写接口必须重新校验。
- 当前列表采用客户端筛选。当单页记录稳定超过约 1,000 条时，再单独设计服务端查询和分页。
- 自动过期、永久删除、容量统计和跨草稿类型统一属于后续治理路线，不在本轮顺带实现。
