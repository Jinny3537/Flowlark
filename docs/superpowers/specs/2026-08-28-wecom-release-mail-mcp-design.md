# 企业微信 MCP 正式发版邮件设计

## 背景

Flowlark 当前将“创建版本”和“设为基线”拆成两个动作。创建的新版本仍可编辑，不能直接代表正式发版；设为基线才表示评审完成并成为当前交付版本。现有团队通知支持企业微信消息，但不支持企业微信邮件，也没有把设基线、Git 同步和发版通知收敛成一次可恢复的操作。

本设计新增“正式发版”动作，并通过企业微信官方 `wecom-cli` 背后的 MCP 能力发送发版邮件。

## 已确认需求

- 在 Flowlark 内完成接入，不做需求池或迭代同步。
- 新增独立的“正式发版”动作。
- 严格执行：设为基线 → Git 同步 → 发送企业微信邮件。
- Git 同步失败时不发送邮件。
- 邮件失败不回滚基线或 Git，进入待重试队列。
- 每个项目保存默认收件人、抄送人、主题模板和正文模板。
- 正式发版时可调整当次收件人和抄送人，不覆盖项目默认值。
- 收件人使用企业微信成员姓名配置，通过通讯录动态解析。
- 邮件主题和正文采用项目自定义模板。
- 邮件不包含 Flowlark 原型链接。
- Flowlark 自动管理本地 MCP Sidecar，用户不需要单独启动服务。

## 非目标

- 不发送附件、内嵌图片、日程邀请或会议邀请。
- 不支持外部邮箱地址、密送、邮件回复和转发。
- 不同步企业微信文档、智能表格、待办、日程或会议。
- 不把 Bot ID、Secret、access token 或企业微信内部 ID 写入 Git。
- 不把“创建待评审版本”改名或等同于正式发版。

## 架构

### 正式发版编排器

核心层提供单一正式发版入口。浏览器 API 和未来 CLI 命令均复用该入口，避免两套发版规则。

编排器分为两个阶段：

1. 预检：只读检查版本、Git、企业微信授权、收件人和模板，并返回可展示的邮件预览。
2. 执行：设基线、Git 同步、持久化邮件任务并调用 MCP 发送。

### 企业微信 MCP Sidecar

`flowlark serve` 启动时自动拉起独立 Node 子进程：

- 只监听 `127.0.0.1`。
- 使用系统分配的随机端口。
- 主进程关闭时一并退出。
- 启动失败或企业微信未授权时不阻止 Flowlark 工作台启动，只将企业微信能力标记为不可用。
- 主进程与 Sidecar 之间使用每次启动随机生成的 Bearer Token；Token 只存在于进程内存和子进程环境中。
- Sidecar 不读取 Flowlark 仓库，只接收解析姓名或发送邮件所需的最小数据。

Sidecar 提供无状态 Streamable HTTP MCP 端点 `/mcp`，支持 `initialize`、`ping`、`tools/list` 和 `tools/call`。为兼容 Flowlark 现有 MCP 客户端，也允许在同一进程级 Token 下直接调用 `tools/call`。

### MCP Tools

#### `wecom_auth_status`

检查 `wecom-cli` 是否存在、版本是否满足要求以及授权状态。该工具只返回可展示状态和修复建议，不返回 Bot ID、Token 或内部路径。

Annotations：只读、幂等、访问外部系统。

#### `wecom_contacts_resolve`

输入企业微信成员姓名数组，逐个调用官方通讯录搜索。每个姓名分别返回：

- `unique`：唯一命中，可继续发版。
- `ambiguous`：返回最多 5 个候选人的姓名、别名、部门和职务。
- `missing`：无匹配。
- `limited`：结果受到服务端限制，需要补充部门或职位信息。

候选人的 `userid` 仅存在于 MCP structured content 的内部字段中，浏览器界面不得显示。

Annotations：只读、幂等、访问外部系统。

#### `wecom_release_mail_send`

输入已解析的收件人、抄送人、主题、Markdown 正文和幂等键。Sidecar 将正文写入权限为 `0600` 的临时 `.md` 文件，调用 `wecom-cli mail send`，并在 `finally` 中删除临时文件。

输出只包含成功状态、主题和收件人数，不向 Flowlark 返回或展示 `mail_id`。

Annotations：写操作、非只读、非破坏性、访问外部系统。工具本身不替代 Flowlark 的持久化幂等队列。

## 数据存储

### 项目共享配置

项目的 `project.json` 新增可选字段：

```json
{
  "releaseMail": {
    "enabled": true,
    "to": ["张三", "李四"],
    "cc": ["王五"],
    "subjectTemplate": "【发版】{{project}} {{version}}",
    "bodyTemplate": "# {{project}} {{version}}\n\n{{changes}}"
  }
}
```

该配置随 Git 同步给团队。规范化规则：姓名去首尾空白、去重并保留顺序；主题和正文限制长度；关闭功能时保留模板，方便再次启用。

### 本机邮件任务

运行时任务写入 `.flowlark/cache/release-mails.json`，不进入 Git。每条任务包含：

- 稳定任务 ID 和幂等键。
- 项目、版本、`baselineAt`。
- 冻结后的主题和 Markdown 正文。
- 已选择的收件人和抄送人解析结果。
- `pending` 或 `sent` 状态。
- 尝试次数、最后错误、创建时间、更新时间和发送时间。

内部 `userid` 可以存入本机 cache，但 API 返回和日志必须剔除。

幂等键格式：

```text
release-mail:<project>:<version>:<baselineAt>
```

## 模板

首期支持以下变量：

| 变量 | 内容 |
| --- | --- |
| `project` | 项目名称 |
| `projectCode` | 项目代码 |
| `version` | 版本号 |
| `title` | 版本标题 |
| `previousBaseline` | 上一基线版本号，没有时为空 |
| `releasedAt` | 预检生成并在执行时冻结的发版时间 |
| `releasedBy` | Git 提交身份姓名 |
| `changes` | Markdown 变更列表 |
| `requirements` | Markdown 关联需求列表 |

模板中的未知变量、空主题或空正文均为阻断错误。为保证预览与实际邮件一致，预检返回 `releasedAt`，执行请求携带该值并由服务端重新校验和渲染。

## 正式发版数据流

### 预检

1. 读取项目和目标版本。
2. 复用现有设基线规则，检查废弃状态、评审疑问、原型文件和变更日志。
3. 检查 Git 仓库、提交身份、冲突和远端配置。
4. 调用 `wecom_auth_status`。
5. 合并项目默认收件人与当次调整。
6. 调用 `wecom_contacts_resolve`，唯一命中才通过；同名时要求用户在候选人中明确选择。
7. 使用固定的 `releasedAt` 和 Git 身份渲染主题、正文。
8. 返回阻断项、警告、候选人和最终邮件预览，不写任何项目数据。

### 执行

1. 服务端重新执行关键预检，防止预览后状态变化。
2. 将目标版本设为基线。如果目标已经是同一基线且尚未发送邮件，则视为失败续跑，不报 `ALREADY_BASELINE`。
3. 执行 Git 提交、拉取和推送，提交说明为 `release: <project>/<version>`。
4. Git 成功后先写入 `pending` 邮件任务，再调用 `wecom_release_mail_send`，避免进程崩溃造成任务丢失。
5. 发送成功后标记 `sent`；失败时保留 `pending` 并记录可展示错误和修复建议。
6. 返回正式发版结果。邮件失败时版本仍是正式基线且已同步 Git，界面明确显示“已发版，邮件待重试”。

### 重试和冲突

- 重复点击或 HTTP 重试命中同一幂等键，不重复发送。
- Git 失败后重试，从 Git 同步继续，不重复设置基线。
- 邮件失败后只重试邮件，不重复设置基线或创建 Git 提交。
- 已发送任务再次请求直接返回既有成功结果。
- 失败期间基线改成其他版本时停止自动重试，并返回基线冲突。
- Sidecar 重启后通过本机任务文件继续重试；发送成功但主进程在落盘前崩溃的极窄窗口无法从企业微信查询幂等结果，界面必须提示人工核对，不能静默重复发送。

## API

新增接口：

- `POST /api/versions/:slug/:no/formal-release/preflight`
- `POST /api/versions/:slug/:no/formal-release`
- `GET /api/release-mails`
- `POST /api/release-mails/:id/retry`

项目邮件配置通过现有项目更新接口写入 `project.json`，不另建第二套项目配置 API。

所有写接口继续受现有本机写权限、局域网只读和镜像只读闸门保护。

## 界面

### 项目编辑

在项目编辑弹窗增加“发版邮件”区域：

- 启用发版邮件开关。
- 默认收件人姓名标签输入。
- 默认抄送人姓名标签输入。
- 主题模板输入。
- Markdown 正文模板输入。
- 支持变量提示。

### 项目版本页

对非废弃版本提供“正式发版”按钮。点击后打开独立弹窗：

1. 读取项目默认配置。
2. 允许当次调整收件人和抄送人。
3. 运行预检并显示版本、上一基线、Git、企业微信授权和收件人解析结果。
4. 同名候选人显示姓名、别名、部门和职务，用户必须明确选择。
5. 展示最终主题和 Markdown 正文预览。
6. 用户点击“确认正式发版”后执行完整流程，按钮进入不可重复提交状态。

结果状态分为：

- 全部成功：基线、Git 和邮件均成功。
- 部分成功：基线与 Git 成功，邮件待重试。
- Git 失败：版本已在本机设为基线但未发邮件，提供继续同步入口。
- 预检失败：不修改任何数据。

创建版本弹窗继续使用“创建待评审版本”，不增加自动发信，避免混淆草稿与正式发布。

## 错误与安全

- `wecom-cli` 未安装：预检提示安装 `@wecom/cli`。
- 版本过低：预检提示升级。
- 未授权：预检提示执行 `wecom-cli auth init`。
- 姓名无匹配或同名未选择：阻止执行，绝不猜测。
- 企业微信业务错误：保留官方 `message` 和 `instruction` 的完整含义，但不展示内部错误码、call ID、`userid` 或 `mail_id`。
- 临时正文文件使用随机文件名、`0600` 权限并在调用后删除。
- Sidecar 不监听局域网地址，不允许无 Token 调用，不设置宽松 CORS。
- 日志不得记录 Bot Secret、Token、完整收件人内部 ID或完整邮件正文。
- 邮件正文是模板渲染结果，不作为命令、路径或 shell 字符串解释；调用 CLI 必须使用 `execFile` 参数数组，不经过 shell。

## 测试设计

### 核心单元测试

- 项目发版邮件配置规范化、去重、长度和未知字段处理。
- 模板变量渲染、未知变量、空主题和空正文。
- 邮件任务的幂等入队、成功、失败和重试。
- API 输出剔除 `userid`、`mail_id` 和凭据。
- Sidecar CLI 错误解析不泄露敏感字段。

### MCP 协议测试

- `initialize`、`ping`、`tools/list`、`tools/call`。
- 无 Token、错误 Token、非回环监听配置均被拒绝。
- 通讯录唯一命中、同名、无匹配和结果受限。
- 邮件正文临时文件权限正确且成功、失败后均删除。
- 工具 annotations 和 structured content 符合契约。

### 编排测试

- 预检阶段无磁盘业务写入。
- 正常顺序严格为设基线、Git 同步、任务入队、邮件发送。
- Git 失败不调用邮件工具。
- 邮件失败保留 pending，基线和 Git 不回滚。
- Git 失败后续跑不重复设置基线。
- 邮件重试不重复 Git 操作。
- 重复请求和服务重启不重复发送已完成任务。
- 基线被其他版本替换时阻止续跑。

### API 与界面测试

- 项目配置读写和 Git 持久化。
- 正式发版预检、执行、结果和邮件重试接口。
- 局域网只读、镜像只读和无写权限状态下按钮禁用、接口拒绝。
- 项目编辑弹窗字段保留和错误定位。
- 正式发版弹窗覆盖成功、同名选择、无匹配、Git 失败和邮件待重试。
- 390px 和桌面宽度无水平溢出；键盘焦点和错误提示可达。

### 回归验证

- 运行 Node 全量测试。
- 运行 Web 模型测试与构建。
- 使用假 `wecom-cli` 完成端到端协议和发版流程验证，不向真实企业微信发送邮件。
- 真实发送只作为用户环境中的最终验收步骤，必须使用测试企业和测试收件人。

## 完成标准

- Flowlark 启动和关闭时能够自动管理 Sidecar，Sidecar 仅监听回环地址。
- 项目能够保存默认收件人、抄送人和自定义模板。
- 正式发版预检能够解析企业微信姓名并阻止歧义或缺失目标。
- 正式发版严格执行设基线、Git 同步、邮件发送，失败可按设计续跑。
- 重试和重复请求不会重复发送已确认成功的邮件。
- 凭据和企业微信内部 ID 不进入 Git、用户界面或普通日志。
- 新增聚焦测试、现有全量测试和 Web 构建均通过。
