# Flowlark v0.7.1–v0.7.5 产品升级设计

## 1. 规划结论

本轮从当前 `v0.7.0` 规划到 `v0.7.5`，以“需求 → 迭代 → 发版 → 验收 → 外部回写 → 归档”为主线，以原型工作效率和发布稳定性为支撑。

采用“业务闭环逐段交付 + 底层风险提前治理”的组合方案：每个小版本都要产生用户可感知的业务结果，同时完成该阶段必需的数据、迁移、同步和恢复能力。

最终目标是：Flowlark 作为需求、迭代、交付和验收状态的主数据源，通过标准化 MCP 接入团队需求或任务平台。项目默认预览后人工确认远程变更；通过验证的可信项目可启用自动回写。

## 2. 已确认的产品决策

1. 规划范围覆盖 `v0.7.1` 至 `v0.7.5`，不按固定人力或周期切分，按产品逻辑划分版本。
2. 主线是需求、迭代、发版、验收和归档闭环。
3. 原型创建和修改效率、安装升级和稳定性作为支撑方向。
4. 闭环终点包括外部需求或任务状态回写和外部迭代结束。
5. 外部平台通过标准化 MCP 接入；本轮不把 GitHub、GitLab、Gitee Issues 的能力扩展作为重点。
6. Flowlark 是主数据源，可以覆盖外部平台中的托管字段。
7. 同步策略按项目配置，默认预览确认；可信项目可以自动回写。
8. 允许升级现有数据结构，但迁移前必须备份，失败后必须恢复。
9. 验收角色和通过规则按项目配置，默认采用产品、研发、测试三方确认。

## 3. 当前基线

当前代码版本为 `v0.7.0`，已经具备以下基础：

- 项目、版本、基线、评审和 Git 协作；
- 需求实体、需求与版本关联；
- 迭代状态机、冻结检查和风险提示；
- 不可变交付快照；
- 正式发版、Git 同步和企业微信发版邮件；
- MCP 客户端、平台能力探测和迭代同步计划；
- 外部任务和 Sprint 的基础映射、预览、冲突检查和续跑日志；
- 原型修改工作台、反馈、跨仓库搜索和只读工作区。

当前主要缺口：

- 需求状态仍以版本关系派生为主，缺少明确且可审计的业务状态机；
- 外部同步能力主要围绕迭代，尚未形成全局同步中心和统一策略；
- 缺少配置化验收角色、不可变验收记录和反馈门禁；
- 正式发版、交付快照、验收、外部任务关闭和迭代归档仍是分散动作；
- 自动回写、失败聚合、迁移恢复和完整审计尚未形成可发布能力。

仓库中已有 `v0.7.1` 的“最近工作续接体验优化”设计和实现。该范围保留，不在本规划中覆盖重做。

## 4. 成功标准

到 `v0.7.5`，一个团队可以完全在 Flowlark 中完成：

```text
创建并确认需求
→ 加入迭代
→ 同步外部任务和 Sprint
→ 冻结并开始迭代
→ 正式发版
→ 生成交付快照
→ 配置角色完成验收
→ 清理阻断反馈
→ 完成外部任务
→ 结束外部 Sprint
→ 自动归档
```

核心成功标准：

1. 全链路无需用户进入外部平台手工修改状态。
2. 每次远程写入都有幂等标识、执行日志和可查询结果。
3. 任一步骤失败后均可从中断点继续，不重复创建或关闭远程对象。
4. 外部平台不可用时，本地浏览和普通编辑仍可使用，界面不会误报同步成功。
5. 现有 `v0.7.0` 数据可自动升级；迁移失败时原数据保持可用。
6. 每个验收结论都能追溯到唯一交付快照、验收角色和操作者。

## 5. 版本路线图

| 版本 | 主题 | 用户成果 | 同步建设的底座 |
|---|---|---|---|
| `v0.7.1` | 续接体验与发布基线 | 快速找到最近项目和版本并继续处理 | 冻结发布范围，完成回归和升级说明 |
| `v0.7.2` | 闭环同步底座 | 统一查看、预览和处理远程变更 | 状态映射、同步策略、审计、队列、迁移恢复 |
| `v0.7.3` | 需求与迭代主导 | 在 Flowlark 管理需求和迭代并更新外部任务、Sprint | 实体映射、批量同步、漂移检测、冻结门禁 |
| `v0.7.4` | 发版与配置化验收 | 完成正式发版、多角色验收和反馈闭环 | 验收记录、交付快照、反馈门禁、状态回写计划 |
| `v0.7.5` | 自动闭环与稳定交付 | 可信项目自动回写、关闭外部对象并归档 | 幂等续跑、冲突审计、健康检查和恢复演练 |

### 5.1 v0.7.1：续接体验与发布基线

定位：整理并正式交付当前已经基本完成的工作，不新增闭环业务模型。

范围：

- 工作台突出最近项目和最近版本；
- 一次点击进入可继续处理的版本；
- 统一项目列表、项目版本页和版本工作台的状态表达；
- 完成桌面端、移动端和只读模式回归；
- 明确发布提交范围并更新版本号、变更日志和升级说明。

验收：

- 用户在 10 秒内识别最近工作，最多点击一次进入目标版本；
- Web 构建、全量测试和核心人工任务通过；
- 不将后续业务闭环能力混入该版本。

明确不做：

- 不修改需求、迭代、交付、权限或 Git 数据模型；
- 不新增外部自动写入；
- 不增加一级业务模块。

### 5.2 v0.7.2：同步与迁移底座

定位：建立安全、可解释、可恢复的远程写入基础。

范围：

- 新增全局同步中心，展示待确认、执行中、失败、漂移、暂停和成功记录；
- 增加项目级同步策略，支持 `manual` 和 `trusted-auto` 两种配置；
- `trusted-auto` 在本版本只完成配置和资格验证，不自动执行；
- 同步预览展示本地当前值、外部当前值、目标值、字段范围和影响对象；
- 建立统一状态映射、实体映射、同步事件和审计记录；
- 每次远程变更携带幂等标识，并保存外部对象版本或 `revision`；
- 数据结构升级前自动备份，迁移失败时恢复原数据；
- MCP 不可用时允许本地编辑，将远程操作标记为待同步。

验收：

- 所有远程写入都必须先生成确定性预览；
- 预览后数据发生变化时，旧计划失效；
- 审计与错误日志不包含密码、Token、认证 Header 或环境变量；
- 迁移任一步骤失败后，旧数据仍可由旧流程读取。

明确不做：

- 不自动修改外部平台；
- 不加入验收角色和自动归档；
- 不允许浏览器指定或调用任意 MCP 工具。

### 5.3 v0.7.3：需求与迭代由 Flowlark 主导

定位：打通“需求确认 → 加入迭代 → 冻结”的前半段闭环。

范围：

- 建立 Flowlark 主导的明确需求状态；
- 本地需求与外部任务建立稳定映射；
- 支持创建、更新和重新绑定外部任务；
- 本地迭代与外部 Sprint 建立稳定映射；
- 支持把迭代需求批量创建或移动到外部 Sprint；
- 冻结检查覆盖需求状态、版本确认、规格、变更、外部映射、写权限和版本冲突；
- 检测外部托管字段漂移，并以 Flowlark 数据生成恢复本地值的方案；
- 所有远程写入继续采用预览后人工确认。

验收：

- 用户能从 Flowlark 创建需求、组织迭代并同步到测试 MCP 平台；
- 冻结后，本地迭代与外部 Sprint 的需求范围一致；
- 重复执行同步不会重复创建任务或 Sprint；
- 同一需求在同一外部项目中最多绑定一个主任务。

明确不做：

- 不自动覆盖外部状态；
- 不结束外部 Sprint；
- 不把外部平台特有字段写入核心业务模型。

### 5.4 v0.7.4：正式发版与配置化验收

定位：打通“正式发版 → 验收 → 反馈处理”的后半段闭环。

范围：

- 项目可配置验收角色、必选角色和通过规则；
- 默认角色为产品、研发、测试，默认全部必选角色通过；
- 验收结论支持待验收、通过、拒绝、有条件通过和豁免；
- 每次验收记录验收人、角色、结论、备注、时间和交付快照；
- 历史结论不可覆盖，修订使用追加记录；
- 正式发版生成不可变交付快照，包含版本、规格、变更、需求、附件和验收规则；
- 未解决反馈分为阻断、重要和一般；
- 存在阻断反馈或必选角色未通过时，不能完成验收；
- 人工确认后将需求、任务和 Sprint 更新为目标状态。

验收：

- 一个迭代可以完成正式发版，并由配置角色完成验收；
- 任一拒绝或阻断反馈都会阻止归档；
- 验收记录始终能够追溯到唯一交付快照；
- 修改项目验收规则不会改变历史交付的验收口径。

明确不做：

- 不自动触发远程写入；
- 不因外部同步失败撤销本地交付快照；
- 不引入 Flowlark 用户账号体系。

### 5.5 v0.7.5：可信项目自动闭环

定位：把经过验证的人工流程升级为可靠自动化。

范围：

- 通过资格验证的项目可启用自动回写；
- 自动回写只修改 Flowlark 管理的托管字段；
- 需求确认、迭代冻结与开始、正式发版、验收完成、需求完成和迭代归档可以触发自动同步；
- 同步失败进入可恢复队列，支持重试、续跑和人工接管；
- 外部托管字段漂移时记录覆盖前后的值；
- 外部对象删除、映射失效或权限变化时暂停自动化；
- 满足全部归档门禁后，自动完成外部任务、结束 Sprint 并归档迭代；
- 增加同步健康检查、失败聚合、迁移恢复演练和审计导出。

验收：

- 测试 MCP 平台上的完整链路无需手工修改远端状态；
- 网络中断后恢复可续跑，不重复创建、评论、通知或关闭对象；
- 每次外部覆盖都能查到触发来源、操作者、前后值和结果；
- MCP 长期不可用时，本地数据不损坏且不会误显示为同步成功。

明确不做：

- 不支持一个项目同时启用多个外部主平台；
- 不自动处理外部对象删除或权限变化；
- 不允许自动取消需求或 Sprint。

## 6. 业务状态设计

### 6.1 需求状态

```text
草拟 → 已确认 → 开发中 → 待验收 → 已完成 → 已归档
         ↑          │
         └── 验收拒绝后重新进入开发
```

| 状态 | 进入条件 | 退出门禁 |
|---|---|---|
| 草拟 | 创建需求 | 标题、范围、负责人和验收标准完整 |
| 已确认 | 产品确认范围 | 已加入迭代并关联有效原型版本 |
| 开发中 | 所属迭代进入进行中 | 对应版本已正式发版 |
| 待验收 | 已生成交付快照 | 必选角色完成验收，阻断反馈清零 |
| 已完成 | 验收规则满足 | 外部任务状态回写成功 |
| 已归档 | 所属迭代归档 | 终态，只能通过显式重新打开恢复 |

需求状态由 Flowlark 保存。外部任务状态是同步结果，不反向决定本地状态。

### 6.2 迭代状态

沿用现有状态机：

```text
计划中 → 评审中 → 已冻结 → 进行中 → 已交付 → 已归档
   └──────────────→ 已取消 ←──────────────┘
```

门禁规则：

- 进入评审中：至少包含一个有效需求；
- 进入已冻结：需求已确认、版本已确认、规格和变更完整、外部映射可写且无版本冲突；
- 进入进行中：外部 Sprint 已创建或更新，并验证启动成功；
- 进入已交付：迭代内所有项目完成正式发版，并生成不可变交付快照；
- 进入已归档：验收通过、阻断反馈清零、外部任务关闭、外部 Sprint 结束；
- 进入已取消：必须填写原因并人工确认，可信项目也不能自动执行。

## 7. 验收模型

每个角色可以追加多次验收记录，以该角色最新一条有效记录参与聚合；历史记录不可修改或删除。

聚合规则：

1. 任一必选角色拒绝，验收失败，需求回到开发中。
2. 必选角色尚未全部提交，状态为验收进行中。
3. 必选角色全部通过或豁免，验收通过。
4. 有条件通过只有在条件项全部关闭后才按通过处理。
5. 阻断反馈未清零时，不能完成验收。
6. 可选角色的结论保留，但不阻止交付。
7. 豁免必须填写原因，并记录操作者和时间。

项目验收规则在创建交付快照时复制进快照。一个迭代包含多个项目时，每个项目版本按自己的快照规则验收；所有项目版本均通过后，迭代才算验收通过。

## 8. 同步所有权与托管字段

Flowlark 只覆盖明确声明为托管的外部字段。

任务托管字段：

- 标题；
- 描述和验收标准；
- 优先级；
- 负责人；
- 所属 Sprint；
- 生命周期状态；
- Flowlark 交付链接和版本摘要。

Sprint 托管字段：

- 名称和目标；
- 负责人；
- 开始和结束日期；
- 需求范围；
- 生命周期状态。

外部平台的评论、工时、标签和自定义统计等非托管字段保持不变。

## 9. 同步规则

### 9.1 普通编辑

1. 先保存本地业务数据。
2. 生成同步事件。
3. 根据项目策略进入待确认或自动执行。
4. 远程失败不回滚本地修改，状态显示为待同步。

### 9.2 关键状态流转

1. 保存流转意图。
2. 生成带有效期的同步计划。
3. 校验本地数据未在预览后变化。
4. 执行外部操作。
5. 重新读取外部对象并确认结果。
6. 最后推进 Flowlark 本地状态。

### 9.3 正式发版

```text
发版预检
→ 设置基线
→ Git 同步
→ 创建交付快照
→ 发送发版通知
→ 更新外部任务
→ 进入待验收
```

某一步失败时保留此前已经完成的结果，下次从失败步骤继续。已确认完成的步骤不得重复执行。

### 9.4 自动和人工边界

| 场景 | 默认项目 | 可信自动项目 |
|---|---|---|
| 创建或更新任务 | 预览确认 | 自动 |
| 移入 Sprint | 预览确认 | 自动 |
| 普通状态更新 | 预览确认 | 自动 |
| 覆盖远端托管字段 | 预览确认 | 自动并审计 |
| 结束 Sprint | 人工确认 | 满足归档门禁后自动 |
| 取消 Sprint | 人工确认 | 始终人工确认 |
| 外部对象被删除 | 人工处理 | 暂停自动化 |
| 权限或映射变化 | 人工处理 | 暂停自动化 |

## 10. 异常恢复

| 异常 | 处理方式 |
|---|---|
| MCP 不可用 | 浏览和普通本地编辑可继续；远程相关状态流转暂停 |
| 请求超时且结果未知 | 先查询外部对象，再决定续跑，禁止直接重复创建 |
| 批量同步部分成功 | 按步骤日志从首个未完成操作继续 |
| 预览后本地数据变化 | 原计划失效，重新生成同步计划 |
| 外部托管字段被修改 | 默认展示差异；可信项目可覆盖并记录审计 |
| 外部对象被删除 | 停止同步，要求重新绑定或明确创建新对象 |
| Git 同步失败 | 不创建交付快照，不回写交付状态，修复后续跑 |
| 数据迁移失败 | 自动恢复迁移前备份，继续按旧结构运行 |
| 自动归档失败 | 保持已交付，显示未完成步骤，不伪装为已归档 |

## 11. 数据设计

继续采用文件存储、Git 协作和本机缓存分离的架构。

```text
仓库/
├── flowlark.json
├── projects/
│   └── <project>/
│       ├── project.json
│       └── versions/
├── requirements/
│   └── <code>/requirement.json
├── milestones/
│   └── <name>.json
├── snapshots/
│   └── <name>.json
├── acceptances/
│   └── <snapshot>/<record-id>.json
└── .flowlark/
    ├── oplog.ndjson
    ├── sync-audit.ndjson
    ├── backup/
    └── cache/
        ├── sync-queue/
        ├── sync-plans/
        └── external/
```

存储原则：

- 验收记录一条一个文件，减少多人协作冲突；
- 交付快照保存验收规则副本和交付文件摘要；
- 外部可变详情只放缓存，仓库保存稳定绑定和同步摘要；
- 同步队列、短期计划和备份不进入 Git；
- 团队审计使用追加式脱敏记录；
- 迁移不修改原型 HTML 或规格书内容。

主要字段变化：

- `project.json`：同步模式、服务和项目映射、托管字段、验收角色和通过规则；
- `requirement.json`：明确生命周期、状态变更元信息、外部任务绑定和最近同步摘要；
- `milestone.json`：外部 Sprint 绑定、生命周期记录、交付快照、验收聚合和同步摘要；
- `snapshot.json`：交付文件摘要、冻结范围、验收规则、反馈统计和完整性结果。

## 12. 系统模块

| 模块 | 单一职责 |
|---|---|
| 生命周期服务 | 校验需求和迭代状态能否流转 |
| 验收服务 | 保存不可变记录并计算聚合结论 |
| 同步计划器 | 对比本地、缓存和远端，生成确定性执行计划 |
| MCP 适配器 | 把标准业务操作翻译为具体 MCP 工具调用 |
| 同步执行器 | 按依赖顺序执行、验证、续跑和防重 |
| 同步队列 | 管理待确认、自动执行、失败和暂停任务 |
| 审计服务 | 记录触发来源、操作者、前后值和结果 |
| 迁移服务 | 预检、备份、迁移、校验和恢复 |
| 快照服务 | 固化交付材料、验收规则和内容摘要 |

本轮不建设通用工作流引擎，也不抽象为安装式插件系统。MCP 平台差异继续由专用适配器承担，核心业务只依赖稳定的标准操作接口。

## 13. 页面与入口

### 13.1 全局同步中心

作为独立页面，并在主导航显示待处理数量。页面按待确认、执行中、失败、漂移、暂停和成功分组。每条记录可以查看差异、确认执行、重试、放弃或进入关联对象。批量确认只能处理普通风险操作。

### 13.2 项目设置

增加两个配置区：

- 外部平台：MCP 服务、外部项目映射、连接测试和托管字段；
- 验收规则：角色、必选角色、通过条件和自动同步开关。

启用可信自动模式前，必须通过连接、权限、创建更新、状态回写和幂等测试。

### 13.3 需求详情

增加明确生命周期、下一步动作、外部任务绑定、同步状态、所属迭代、交付版本、验收结论、阻断反馈和同步预览入口。

### 13.4 迭代详情

每个阶段只展示一个主要动作：

- 计划中：完善范围；
- 评审中：解决冻结阻塞；
- 已冻结：同步并开始 Sprint；
- 进行中：完成正式发版；
- 已交付：推进验收；
- 验收完成：结束 Sprint 并归档。

页面同时展示本地状态、外部状态和不一致原因。

### 13.5 交付与验收

交付快照详情增加材料完整性、需求和版本清单、反馈阻塞项、各项目验收矩阵、验收历史和外部回写进度。验收入口放在交付详情和迭代详情，不增加独立一级验收模块。

## 14. 数据流

```text
用户操作
→ 生命周期预检
→ 保存本地业务数据或流转意图
→ 生成同步事件
→ 人工确认或可信项目自动执行
→ MCP 写入
→ 重新读取远端验证
→ 保存绑定与审计
→ 重新计算需求、迭代和验收状态
```

## 15. 核心不变量

1. 一个项目同时只启用一个外部主平台。
2. 一个本地需求在同一外部项目中最多绑定一个主任务。
3. 一个迭代最多绑定一个主 Sprint。
4. 所有远程写入必须存在幂等标识和审计记录。
5. 未验证远程结果，不推进依赖该结果的本地状态。
6. 已完成步骤不因后续失败而静默回滚。
7. 离线状态不能显示为同步成功。
8. 只有不可变交付快照能够成为验收依据。
9. 自动回写只覆盖声明的托管字段。
10. 取消、删除、映射失效和权限变化不能无人值守执行。

## 16. 优先级

| 版本 | P0：缺失则不能发布 | P1：应完成 | 延后 |
|---|---|---|---|
| `v0.7.1` | 最近工作续接、跨页上下文、回归和发布边界 | 响应式细节和状态文案 | 业务闭环新能力 |
| `v0.7.2` | 自动迁移与恢复、确定性计划、人工确认、审计 | 同步中心、失败队列 | 自动回写 |
| `v0.7.3` | 需求任务和迭代 Sprint 映射、状态回写、冻结门禁 | 批量同步、漂移对比 | 验收和自动归档 |
| `v0.7.4` | 配置化验收、不可变记录、反馈门禁、快照绑定 | 验收矩阵和历史体验 | 无人值守自动化 |
| `v0.7.5` | 可信自动回写、幂等续跑、外部关闭、自动归档 | 健康看板、审计导出 | 多平台并行和通用工作流 |

任何新增功能进入当前版本时，必须明确替换或延后一个同等工作量的 P1 项，不能挤压 P0。

## 17. Go / No-Go 发布条件

每个版本只有同时满足以下条件才能发布：

- 所有 P0 验收通过；
- 不存在未解决的严重或阻断缺陷；
- `npm test` 和 Web 构建通过；
- 新仓库初始化通过；
- 从上一正式版本升级通过；
- 迁移失败恢复测试通过；
- 只读和离线模式没有功能倒退；
- 更新日志、升级说明和恢复说明完整；
- 实际发布提交范围已经冻结。

从 `v0.7.2` 开始额外要求：

- 测试 MCP 的成功路径通过；
- 超时、断网、权限不足和部分成功路径通过；
- 日志中不存在密钥或认证信息；
- 重复执行不会重复创建远程对象。

## 18. 测试策略

每版至少验证三类端到端场景：

1. 正常路径：一次完成目标流程。
2. 中断路径：在每个外部步骤注入失败，再恢复续跑。
3. 并发与漂移：预览后本地或远端数据发生变化，旧计划失效或进入冲突处理。

共同验证矩阵：

- 生命周期合法和非法流转；
- 验收角色聚合、拒绝、豁免和有条件通过；
- 反馈门禁；
- 同步计划确定性和有效期；
- 幂等执行和未知结果复查；
- 部分成功后的步骤级续跑；
- 数据迁移、引用校验和恢复；
- 全新仓库、现有仓库、只读仓库和离线模式；
- MCP 缺失工具、权限不足、协议错误和进程退出；
- Git 同步失败和恢复；
- 桌面端和移动端核心流程。

## 19. 主要风险

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 覆盖外部平台中的有效修改 | 团队数据丢失或误更新 | 只覆盖托管字段，记录前后值；删除、权限变化和映射失效始终暂停 |
| 自动化重复任务或通知 | 外部数据污染 | 幂等键、远端结果复查、步骤级执行日志 |
| 批量操作部分成功 | 本地和远端状态割裂 | 独立步骤、完成点持久化、从首个未完成步骤续跑 |
| 数据迁移损坏仓库 | 用户无法继续工作 | 修改前备份、迁移后引用校验、失败自动恢复 |
| 多人同时验收 | Git 冲突 | 每条验收记录使用独立不可变文件 |
| 无账号体系导致身份弱 | 验收责任不清 | 同时记录本机或 Git 身份和外部身份，明确身份来源，不声称强认证 |
| MCP 服务契约变化 | 同步不可用 | 启动时探测能力，缺少必需工具时禁用写入并展示诊断 |
| 正式发版中途失败 | 状态不一致 | 固定步骤顺序、已完成步骤不回滚、清晰展示停点 |
| 小版本范围膨胀 | 无法稳定发布 | 每版限定一个用户成果，多平台、通用插件化和账号系统明确延后 |

## 20. v0.7.x 统一非目标

- 不建设中心化服务器或 Flowlark 账号体系；
- 不同时连接多个外部任务平台；
- 不让外部平台反向覆盖 Flowlark 核心状态；
- 不让 AI 自动决定验收结论或关闭反馈；
- 不替换现有 Git、企业微信邮件和本地优先架构；
- 不建设通用 BPM、工作流编排器或开放插件市场；
- 不扩展与本轮闭环无关的搜索、视觉或管理模块。

## 21. 交付清单

- 五个版本的独立发布范围和退出条件；

- `v0.7.5` 完整闭环人工验收记录。

## 22. 后续实施顺序

本设计获批后，按以下顺序拆分实施计划：

1. 先确认 `v0.7.1` 实际发布基线和未发布提交范围。
2. 为 `v0.7.2` 单独编写数据迁移、同步事件和同步中心实施计划。
3. `v0.7.2` 发布并通过恢复演练后，再规划 `v0.7.3` 的业务状态和外部映射实现。
4. 验证人工同步在真实测试项目中稳定后，再进入 `v0.7.4` 验收设计实现。
5. 只有人工闭环达到稳定标准，才允许在 `v0.7.5` 开放可信自动模式。

每个版本分别形成实施计划、验收记录和发布说明，不使用一份跨五个版本的超大实现计划。
