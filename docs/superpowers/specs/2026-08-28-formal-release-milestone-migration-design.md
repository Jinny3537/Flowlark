# 正式发版迁移至迭代模块设计

日期：2026-08-28
状态：已确认

## 1. 背景

当前“正式发版”入口位于项目版本页，并直接以 `project + version` 调用版本域接口。该流程依次完成：

1. 将目标版本设为项目当前基线；
2. 提交、拉取并推送 Git；
3. 通过企业微信 MCP 发送发版邮件。

迭代模块已经维护本轮交付的版本范围和完整生命周期。正式发版继续留在项目版本页，会绕过迭代状态和范围约束，无法保证正在发布的版本属于当前执行中的迭代。

## 2. 目标

- 将正式发版入口从项目版本页迁移到迭代详情页的“版本范围”表格。
- 继续按单个项目版本发版，不增加迭代批量发版。
- 仅允许处于 `active` 状态的迭代发版。
- 仅允许发布该迭代版本范围内的 `project + version`。
- 同时迁移 HTTP API 归属，避免客户端绕过迭代约束。
- 复用现有基线、Git、邮件队列、重试和幂等能力。
- 发版完成后刷新版本基线和邮件状态，但不自动结束迭代。

## 3. 非目标

- 不提供“一键发布整个迭代”。
- 不修改迭代生命周期或自动执行 `active -> delivered`。
- 不修改企业微信发版邮件模板及项目级默认收件人配置。
- 不把邮件任务改造成迭代级存储结构。
- 不移除“设为基线”这一独立底层操作。
- 不重构与本次迁移无关的项目版本、迭代同步或 Git 功能。

## 4. 选定方案

采用“入口与 API 一起迁移”的方案。

迭代详情页负责提供正式发版入口。新的迭代域服务方法先校验迭代状态和版本归属，再调用现有单版本发版内核。原版本域发版路由和前端 API 方法删除，外部客户端不能再直接绕过迭代校验。

## 5. API 设计

新增两个接口：

```text
POST /api/milestones/:name/versions/:project/:version/formal-release/preflight
POST /api/milestones/:name/versions/:project/:version/formal-release
```

请求体继续使用现有结构：

```json
{
  "to": ["张三"],
  "cc": ["李四"],
  "selections": {},
  "releasedAt": "2026-08-28T10:00:00.000Z"
}
```

预检和执行响应继续使用现有正式发版结构，确保发版弹窗、邮件预览、候选成员选择和结果展示能够复用。

删除旧接口：

```text
POST /api/versions/:project/:version/formal-release/preflight
POST /api/versions/:project/:version/formal-release
```

邮件任务查询和重试接口保持不变：

```text
GET  /api/release-mails
POST /api/release-mails/:id/retry
```

## 6. 服务端设计

### 6.1 迭代发版目标校验

新增一个内部校验函数，接收 `name`、`project` 和 `version`，并完成以下检查：

1. 迭代存在；
2. 迭代状态严格等于 `active`；
3. 迭代 `items` 中至少存在一个 `project` 与 `version` 同时匹配的条目。

需求编号不是发版目标的一部分。同一个项目版本即使关联多个需求，也只代表同一个发版目标。

状态不符合时返回明确的迭代状态冲突。版本不在范围内时返回明确的迭代范围错误。执行接口仍先校验工作区写权限。

### 6.2 双重校验

预检与正式执行分别调用迭代发版目标校验，不能依赖前一次预检结果。这样可阻止以下竞态：

- 预检后迭代被结束、归档或取消；
- 预检后版本被移出迭代范围；
- 客户端直接构造正式执行请求。

### 6.3 复用现有发版内核

现有 `#prepareFormalRelease` 继续负责版本、文件、变更日志、Git 身份、Git 状态、企业微信授权、收件人解析和邮件渲染。

现有正式执行逻辑抽为仅供类内部调用的单版本发版函数。新的公开迭代域方法在校验通过后调用该函数。下列行为保持不变：

- 设置项目基线；
- Git 提交、拉取和推送；
- 邮件任务的幂等键；
- 已发送任务的重复调用短路；
- Git 失败时不发送邮件；
- 邮件失败时进入待重试队列；
- 基线发生变化后禁止重试旧邮件任务。

## 7. 前端设计

### 7.1 项目版本页

移除以下内容：

- “正式发版”按钮；
- `FormalReleaseDialog` 引用；
- 当前选中发版版本的组件状态；
- 项目版本页中的发版弹窗实例；
- 因此变为未使用的图标或导入。

“设为基线”继续保留，便于独立维护项目基线。

### 7.2 迭代详情页

“版本范围”表增加“发版状态”列，并根据最新的同项目同版本邮件任务显示：

| 邮件任务 | 显示状态 |
|---|---|
| 不存在 | 未发版 |
| `sent` | 已发版 |
| `pending` | 邮件待重试 |

最新任务按 `updatedAt`、`createdAt` 的可用时间排序；时间相同时保持接口返回顺序。该状态表示此项目版本最近一次正式发版邮件的结果，不替代旁边的“当前基线 / 基线已变化”标记。

“操作”列根据迭代状态显示不同动作：

| 迭代状态 | 操作 |
|---|---|
| `planning`、`reviewing` | 保留“移除” |
| `active` | 显示“正式发版” |
| `frozen`、`delivered`、`archived`、`canceled` | 不显示发版或移除操作 |

只读工作区仍显示 `active` 状态下的“正式发版”按钮，但按钮禁用。服务端继续执行写权限校验。

### 7.3 打开发版弹窗

用户点击某行“正式发版”后：

1. 并行读取该行对应的完整项目配置和版本详情；
2. 读取失败时留在迭代详情页并显示明确错误，不打开弹窗；
3. 读取成功后打开现有 `FormalReleaseDialog`；
4. 弹窗携带迭代标识，并改用新的迭代域预检和执行接口。

弹窗的布局、收件人编辑、候选成员选择、邮件预览、步骤状态和邮件重试交互保持不变。

### 7.4 操作后刷新

发版返回 `complete`、`mail_pending` 或 `git_failed` 后，继续展示现有结果信息。执行回调重新读取：

- 迭代详情，用于刷新当前基线和风险提示；
- 发版邮件列表，用于刷新该行发版状态。

刷新过程不得调用迭代状态流转接口。

## 8. 错误处理

- 迭代不存在：沿用资源不存在响应。
- 迭代不是 `active`：返回状态冲突，提示只有进行中的迭代可以正式发版。
- 版本不在迭代范围：返回范围错误，提示先核对迭代版本范围。
- 工作区只读：沿用现有写权限错误。
- 版本废弃、评审疑问、原型文件缺失或变更日志不完整：沿用现有正式发版阻塞项。
- Git 身份、冲突、进行中操作或远端缺失：沿用现有 Git 阻塞项。
- 企业微信授权、联系人或邮件模板错误：沿用现有发版邮件阻塞项。
- 邮件发送失败：保留待重试任务，不回滚已经完成的基线和 Git 操作。

## 9. 测试设计

### 9.1 服务与领域测试

- `active` 迭代中的范围内版本可以预检和发版。
- `planning`、`reviewing`、`frozen`、`delivered`、`archived`、`canceled` 均被拒绝。
- `active` 迭代中不属于范围的项目版本被拒绝。
- 预检通过后状态变化或范围变化，正式执行仍被拒绝。
- 同一版本重复发版保持幂等。
- Git 失败和邮件待重试行为保持原语义。

### 9.2 HTTP API 测试

- 新的两个迭代域接口返回正确的预检和执行结果。
- 路径参数经过正确解码并参与范围校验。
- 旧版本域正式发版接口返回 404。
- 公共响应继续隐藏企业微信内部成员 ID 和邮件幂等键。

### 9.3 前端模型与构建验证

- 不同邮件任务集合能够稳定映射为未发版、已发版、邮件待重试。
- 不同迭代状态映射到正确的行操作。
- 项目版本页源码不再包含正式发版入口。
- TypeScript 和 Vite 构建通过。

### 9.4 回归验证

运行正式发版、迭代生命周期、迭代 API 相关定向测试，再运行完整测试套件与 Web 构建。

## 10. 完成标准

- 项目版本页不再出现“正式发版”。
- 迭代详情页仅在 `active` 状态为范围内版本提供“正式发版”。
- 前端和后端都不能通过非进行中迭代或范围外版本执行发版。
- 发版后基线与邮件状态正确刷新，迭代状态保持不变。
- 旧版本域发版 API 已移除。
- 现有单版本发版的幂等、Git 失败和邮件重试语义无回归。
- Web 构建、定向测试和完整测试套件通过。
