# 项目模块原型管理增强设计

## 决策摘要

本次升级采用“主链路渐进增强”方案，保留现有项目版本页作为唯一主入口，围绕以下闭环增强：

`快速发布 → 待评审 → 定稿基线 → 差异查看 → 历史追溯`

产品经理是首要用户，研发和测试是浏览、评审与确认交付的辅助用户。产品形态继续保持本地软件、Git 存储和无自建账号体系，不引入数据库、常驻服务或多人实时编辑。

功能分两期交付：

- 一期解决快速发布、评审状态可见、基线识别和常用对比。
- 二期补齐监听归档、批量处理、基线历史、高级筛选和追溯输出。

## 背景与现状

Flowlark 已经具备完整的底层原型版本能力：

- 项目入口展示最新版本和当前基线。
- 新版本支持文件、粘贴源码和公开 URL 三种导入方式。
- 导入时可以推断版本号与标题、检查外部依赖、填写变更日志和关联需求。
- 项目版本页支持搜索、状态筛选、排序、标记已读、设置基线、回滚、废弃、恢复和删除。
- 版本工作台支持编辑原型、规格、变更、需求、评审状态和标注反馈。
- 对比页支持两个版本或原型与线上系统并排查看，并展示累计变更与修改热点。
- Git 已经提供基线历史、贡献者、同步和冲突恢复能力。

当前问题不是缺少底层能力，而是能力分散在新建弹窗、项目版本页、版本工作台、对比页和 Git 面板中：

1. 产品经理创建版本后，还需要自己判断下一步去哪里评审、同步或定稿。
2. “编辑中”和“待评审”属于两个状态维度，但项目版本页只突出前者，容易误解。
3. 当前基线虽然存在摘要条，但没有直接回答“相对上一基线改了什么”。
4. 常用对比需要进入工作台后再选择目标，路径偏长。
5. 现有高级能力缺少按真实任务组织的快捷入口，用户需要先理解页面结构。

## 目标

- 产品经理从拿到 HTML 到形成可评审版本不超过 3 分钟。
- 研发和测试进入项目后 10 秒内确认当前基线，并看清相对上一基线的变化。
- 将创建、评审、基线、对比和追溯组织为一条连续主链路。
- 复用现有存储、评审、反馈、累计变更、对比和 Git 能力，避免重复系统。
- 所有高影响动作都有明确前置检查、结果反馈和恢复路径。
- 保持现有 CLI、HTTP API、旧项目和旧版本数据兼容。

## 非目标

- 不建设通用任务看板、项目排期、工时或资源管理。
- 不新增账号、组织、成员、角色或审批签名体系。
- 不支持多人同时编辑同一个版本。
- 不做截图级、像素级或源码级自动 diff。
- 不自动判断设计正确性，也不使用 AI 自动生成变更日志。
- 不在创建版本时自动切换基线。
- 不默认自动执行 Git push；同步仍由用户明确触发。
- 不重做项目首页、版本工作台或对比页的视觉体系。

## 成功标准

### 发布提效

在仓库干净、文件有效且无网络异常的标准场景下，产品经理可以完成：

1. 进入项目。
2. 导入 HTML。
3. 确认自动填写的版本号和标题。
4. 填写至少一条变更。
5. 创建待评审版本。
6. 同步到 Git 或复制评审摘要。

从开始导入到看到发布结果不超过 3 分钟，过程中不要求打开第二个业务页面。

### 版本准确

研发或测试进入项目版本页后，无需滚动版本列表即可看到：

- 当前基线版本号与标题。
- 基线确认时间和维护人。
- 相对上一基线的变更数量。
- 是否存在晚于当前基线的待评审或有疑问版本。
- “打开当前基线”和“与上一基线比较”两个直接动作。

使用标准测试数据完成“确认当前开发版本并说出主要变化”的任务不超过 10 秒。

### 兼容与质量

- 旧仓库无需迁移即可使用一期功能。
- CLI 创建的版本继续按现有规则展示。
- 只读用户不能创建、编辑、定稿、回滚或同步，但可以浏览和对比。
- 项目版本页现有键盘选择、移动端详情抽屉和错误恢复行为不退化。
- 不采集远程使用数据；计时验收通过人工可用性任务完成。

## 设计原则

### 1. 一个主入口

项目版本页继续是项目内的唯一主入口。新建版本、当前基线、待评审版本、常用对比和追溯入口都从这里发起，不新增“发布中心”一级导航。

### 2. 先显示结论，再展开细节

页首先回答“当前应该按哪版开发”和“它改了什么”。完整版本元数据、原型编辑、反馈处理和任意版本对比继续放在工作台与对比页。

### 3. 双状态并列

版本生命周期与评审状态分别表达，不再用一个标签混合解释：

| 维度 | 现有值 | 回答的问题 |
|---|---|---|
| 生命周期 | 编辑中、当前基线、历史版本、已废弃 | 版本能否编辑、是否是开发依据 |
| 评审状态 | 待评审、已确认、有疑问、已废弃 | 版本是否经过评审、是否存在问题 |

例如新版本显示为“编辑中 · 待评审”，设置基线后显示为“当前基线 · 已确认”。

### 4. 高影响动作显式确认

创建版本、同步 Git、设置基线和回滚是不同动作。系统可以给出连续的下一步入口，但不能把它们静默合并成一个不可撤销操作。

### 5. 派生信息不落库

待评审数量、晚于基线的版本数、上一基线、对比快捷目标和变更摘要都从现有版本、BASELINE 和 Git 历史派生，不复制进 `project.json`。

## 页面与职责边界

| 页面或组件 | 升级后职责 | 不承担的职责 |
|---|---|---|
| 项目首页 | 选择项目并进入原型管理 | 不展示项目治理报表 |
| 项目版本页 | 快速发布、基线结论、评审队列、常用对比、版本浏览 | 不直接编辑复杂文档和原型 |
| 新建版本弹窗 | 导入、自动填写、发布前检查、创建结果 | 不设置基线 |
| 版本工作台 | 深度编辑、预览、规格、反馈和评审状态维护 | 不承担跨版本总览 |
| 对比页 | 任意版本、基线和线上系统的深度并排对比 | 不承担版本创建 |
| Git 面板 | 同步、权限、冲突和恢复 | 不解释版本业务差异 |

## 一期功能设计

### F01. 快速发布入口

项目版本页右上角保留“新建版本”主按钮。创建成功后不立即关闭整个任务链路，而是进入“发布结果”状态，明确展示版本已创建、评审状态、Git 同步状态和下一步动作。

发布流程沿用单个弹窗，不新增独立页面。表单按任务顺序排列：

1. 原型来源。
2. 版本号和标题。
3. 变更日志。
4. 关联需求与影响面。
5. 发布前检查与提交。

关联需求和影响面默认保持可见但不阻塞；当用户只需要快速发版时，可以不展开历史影响详情。

### F02. 多来源导入与智能填写

继续支持现有三种来源：

- 本地 `.html` 或 `.htm` 文件。
- 粘贴完整 HTML 源码。
- 导入公开 HTTP/HTTPS URL。

自动填写规则：

- 文件名包含可识别版本号时沿用现有推断结果。
- 文件名没有版本号时，根据项目最新版本建议下一个版本号。
- 只对 `v数字.数字` 及其多段形式递增最后一段，例如 `v1.4` 建议 `v1.5`。
- 最新版本不符合上述形式时不猜测，版本号保持为空。
- 版本标题优先取 HTML `<title>`，为空时取文件名或“导入原型”。
- 自动填写值始终可编辑，用户手工修改后不再被后续检查覆盖。

版本号建议是交互便利，不改变服务端唯一性和格式校验规则。

### F03. 一行变更快速录入

变更日志仍使用现有结构化数据，但首行提供紧凑录入方式：

- 类型默认“修改”，可切换新增或删除。
- 位置和说明在同一行完成。
- 需要多条变更时继续添加行。
- 输入位置后可以主动执行现有影响面检查。

除项目首个版本外，“创建待评审版本”要求至少一条有效变更。这样发布结果才具备评审价值，并与后续设置基线的规则一致。

CLI、watch 和底层 `addVersion` 仍允许创建不完整草稿；上述要求只作用于网页“创建待评审版本”主路径。

### F04. 发布前检查

提交前统一生成检查结果，分为阻断项和提醒项。

阻断项：

- 没有有效 HTML。
- 文件类型或大小不合法。
- 版本号为空、格式不合法或已存在。
- 标题为空。
- 非首个版本没有有效变更日志。

提醒项：

- 存在外部资源，离线打开可能不完整。
- 没有关联需求。
- 变更位置命中历史需求或高频修改区域。
- 当前仓库为只读或 Git 远端状态未知。

检查结果定位到对应字段。阻断项清零后才能创建；提醒项允许用户确认后继续。

检查逻辑由 core 提供，前端只负责显示，避免前端检查通过但服务端写入失败。最终写入仍执行完整服务端校验，以处理检查后数据变化的情况。

### F05. 发布结果与下一步

创建成功后展示结果摘要：

- 项目、版本号和标题。
- “编辑中 · 待评审”状态。
- 变更数、关联需求数和外部依赖数。
- 当前基线，以及新版本是否晚于当前基线。
- 当前 Git 状态：仅本地、待同步、已同步或同步失败。

提供三个明确动作：

1. **打开工作台**：进入该版本预览和评审。
2. **同步到 Git**：复用现有 Git 助手；同步失败进入现有冲突恢复流程，不删除已创建版本。
3. **复制评审摘要**：复制项目、版本、当前基线、变更摘要和页面路径的 Markdown，不依赖固定 localhost 地址。

不在创建成功后自动设置基线。产品经理必须在评审完成后单独确认。

### F06. 基线指挥条

现有基线摘要条升级为项目版本页的首要结论区，固定展示：

- 当前基线版本号与标题。
- 基线确认时间与维护人。
- 相对上一基线累计新增、修改、删除的数量。
- 当前基线关联需求数。
- 晚于基线的待评审版本数和有疑问版本数。

主要动作按以下顺序展示：

1. 打开当前基线。
2. 与上一基线比较。
3. 查看待评审版本。
4. 回滚上一基线，仅在满足现有回滚条件且当前可写时显示。

项目尚无基线时，指挥条显示“尚未设置开发基线”，并引导从有变更日志的版本中选择，而不是展示空白指标。

### F07. 评审队列与双状态筛选

版本索引增加任务型快捷筛选：

- 全部版本。
- 待评审。
- 有疑问。
- 基线历史。
- 已废弃。

每个版本同时显示生命周期和评审状态。现有文本搜索继续覆盖版本号、标题、标签和需求号；排序继续支持最新优先和最早优先。

“待评审”定义为 `reviewStatus = pending` 且版本未废弃；“有疑问”定义为 `reviewStatus = questions`。当前基线即使 `reviewStatus = confirmed`，仍通过基线标记独立突出。

### F08. 常用对比快捷入口

项目版本页提供三个无需再次选择目标的对比入口：

- 当前基线 vs 上一基线。
- 当前选中版本 vs 当前基线。
- 最新非废弃版本 vs 当前基线。

只有目标有效且两个版本不相同时才显示入口。点击后进入现有对比页，并通过 URL 查询参数固定两侧版本，保证刷新和复制链接后结果一致。

选中版本详情中增加“与当前基线比较”。基线指挥条增加“与上一基线比较”。完整的任意版本选择仍在对比页完成。

### F09. 基线确认前检查

“设为基线”确认框在写入前展示：

- 将被替换的当前基线。
- 候选版本的标题、评审状态和变更数。
- 相对当前基线的累计变更摘要。
- 关联需求和外部依赖提醒。
- 基线切换后将触发的通知渠道。

阻断规则：

- 已废弃版本不能设为基线。
- 非首个且从未成为基线的版本必须有变更日志。
- 评审状态为“有疑问”时不能设为基线；产品经理需先处理问题并调整评审状态。

没有关联需求、存在外部依赖或本地反馈草稿只作为提醒，不作为阻断项，因为本地反馈草稿不具备可靠的远端解决状态。

### F10. 基线操作结果

基线切换成功后展示：

- 新基线版本。
- 上一基线版本。
- 变更摘要。
- 通知发送结果。
- “打开基线”“复制基线摘要”“查看对比”动作。

基线写入成功但通知失败时，明确显示“基线已更新，通知发送失败”，不能把整个操作误报为失败，也不能回滚已经完成的基线切换。

## 二期功能设计

### F11. 项目内监听归档入口

在项目版本页显示当前项目的 watch 待归档数量。点击后打开现有监听草稿处理能力，并自动限定当前项目。

产品经理可以从监听项直接进入快速发布表单，复用智能填写、变更录入和发布前检查。归档失败继续使用现有重试机制。

### F12. 多文件发布队列

拖入多个 HTML 文件时先生成本地发布队列，不直接批量写入：

- 每个文件独立推断版本号和标题。
- 重复版本号、非法文件和缺少变更的条目单独标错。
- 用户逐条确认或移除后按顺序创建。
- 单条失败不撤销已成功条目，结果页逐条说明成功与失败。

批量队列只服务于同一项目，不跨项目批量发布，避免复杂的项目匹配规则。

### F13. 复用上一版元数据

新建版本时可以选择“参考上一版”，只复制适合复用的编辑结构：

- 关联需求候选。
- 标签。
- 变更日志的常用位置候选。

不复制旧变更说明、不复制版本标题、不自动继承原型文件，避免把历史事实误当成当前变更。

### F14. 基线历史时间线

项目版本页增加“基线历史”抽屉，复用现有 Git 基线历史接口展示：

- 基线版本。
- 切换时间。
- 操作人。
- Git 提交。
- 从该基线到下一基线的累计变更入口。

Git 历史不可用时显示原因和恢复建议，不伪造本地时间线。

### F15. 高级筛选与可分享视图

在现有搜索基础上增加组合条件：

- 生命周期。
- 评审状态。
- 是否为基线历史。
- 创建人。
- 时间范围。
- 关联需求。
- 是否有外部依赖。

筛选条件写入 URL 查询参数，刷新或复制链接后保持一致。个人最近使用的筛选可以保存在 `.flowlark/cache`，不写入业务仓库；团队共享视图继续复用现有保存视图能力。

### F16. 追溯摘要导出

累计变更和基线对比支持复制或导出 Markdown 摘要，内容包括：

- 项目与版本区间。
- 新增、修改、删除数量。
- 按位置分组的变更。
- 高频修改区域。
- 关联需求。
- 两侧版本路径。

导出不包含原型 HTML，不取代现有离线交付包。

### F17. 回滚影响预览

执行“回滚上一基线”前展示：

- 当前基线与目标基线。
- 将撤回的累计变更。
- 受影响需求。
- 通知渠道。

确认后继续调用现有回滚能力。回滚完成后使用与基线切换相同的结果摘要，保证用户能确认实际生效版本。

## 数据与业务规则

### 一期存储

一期不新增持久化字段，继续使用现有数据：

- `status` 表达 DRAFT、READY、VOID。
- `reviewStatus` 表达 pending、confirmed、questions、obsolete。
- `BASELINE` 文件表达当前基线。
- `baselineAt` 与 Git 历史用于派生基线历史。
- `changes`、`requirements` 和 `externalRefs` 用于发布检查和差异摘要。

因此旧仓库无需 schema 迁移。

### 上一基线判定

页面快捷对比使用以下顺序确定上一基线：

1. 优先使用现有 Git 基线历史中，当前基线之前最近一次不同的基线。
2. Git 历史不可用时，使用非当前、未废弃且 `baselineAt` 最近的版本作为降级结果。
3. 两种方式都无法得到结果时，显示“暂无上一基线”，不使用普通最新版本代替。

降级结果在界面上标明“根据本地版本记录推断”，避免与 Git 历史混淆。

### 评审与基线

- 新建网页版本继续写入 `status = DRAFT`、`reviewStatus = pending`。
- 评审状态为 questions 时禁止向前设置为新基线。
- 设置基线成功后继续由 core 写入 `status = READY`、`reviewStatus = confirmed`。
- 废弃与恢复继续沿用现有状态联动。
- 回滚曾经的基线沿用现有豁免规则，不被空变更日志阻断。

## API 与组件边界

### 新增发布前检查接口

建议新增只读检查接口：

`POST /api/projects/:slug/version-preflight`

请求包含版本号、标题、原始 HTML、变更和需求。服务端复用现有 HTML 检查与业务规则生成结果，返回：

```json
{
  "ready": false,
  "blockers": [
    { "code": "CHANGELOG_REQUIRED", "field": "changes", "message": "请至少填写一条变更" }
  ],
  "warnings": [
    { "code": "EXTERNAL_REFS", "message": "检测到 2 个外部依赖" }
  ]
}
```

接口不写文件、不占用版本号，也不替代最终创建校验。

### 现有接口复用

- 创建版本继续使用 `POST /api/projects/:slug/versions`。
- 累计变更继续使用 `/api/projects/:slug/cumulative`。
- 基线设置、回滚、评审状态、反馈、Git 同步和基线历史继续复用现有接口。
- 对比页继续使用查询参数 `a`、`b`、`mode` 和 `changes`。

### 前端组件

- `NewVersionDialog` 承担快速发布与发布结果，不引入第二套创建表单。
- `ProjectVersions` 派生基线摘要、评审队列和常用对比目标。
- `Compare` 接收快捷预设，不复制累计变更算法。
- 新增纯模型函数负责版本号建议、任务型筛选和快捷对比目标，并通过 Node 单元测试固定规则。
- 业务阻断规则放在 core，React 组件不复制服务端判断。

## 错误与恢复

- 导入失败时保留已填写的版本信息、变更和需求，允许更换来源后重试。
- 发布前检查失败只定位问题，不清空表单。
- 检查通过后版本号被其他进程占用时，创建接口返回冲突并聚焦版本号字段。
- 创建成功但 Git 同步失败时，版本继续保留；用户进入 Git 面板处理冲突后重试同步。
- 基线成功但通知失败时，不回滚基线，只保留通知重试入口。
- 累计变更读取失败时，对比页仍可展示两侧原型，并单独提示摘要不可用。
- Git 基线历史不可用时使用明确降级或空状态，不阻塞当前基线浏览。
- 只读模式隐藏或禁用所有写动作，保留对比、下载、标记已读和复制摘要。

## 测试与验收

### Core 与 API

- 发布前检查覆盖文件、版本号、标题、重复版本和变更日志阻断项。
- 首个版本允许没有变更，后续待评审版本必须有变更。
- 外部依赖、无需求和历史影响只返回提醒，不阻断创建。
- 评审状态为 questions 的版本不能设置为新基线。
- 回滚曾经的基线继续通过现有变更日志豁免。
- 基线写入成功但通知失败时返回可区分结果。
- Git 历史与本地 `baselineAt` 降级得到正确的上一基线。

### 前端模型

- `v1.4` 建议 `v1.5`，`v2.3.9` 建议 `v2.3.10`。
- 非数字版本名不产生建议。
- 用户手工修改版本号或标题后，重新检查来源不覆盖输入。
- 待评审、有疑问、基线历史和已废弃筛选结果正确。
- 三类常用对比在目标缺失或相同时不显示。
- 发布结果能区分仅本地、待同步、已同步和同步失败。

### 页面回归

- 项目版本页现有搜索、排序、键盘选择和移动端抽屉继续工作。
- 新建版本的文件、粘贴和 URL 三种来源都能完成创建。
- 只读状态不能创建、同步、设置基线或回滚。
- 对比快捷入口使用稳定 URL，并在刷新后保持相同版本组合。
- 基线指挥条在无版本、无基线、只有一个基线和多个历史基线时都有明确状态。
- 390、768、1024 和 1440px 视口无按钮遮挡或页面横向溢出。
- 页面运行时错误和浏览器控制台错误为空。

### 可用性验收

准备一个包含当前基线、两个历史基线和一个待评审版本的标准项目，执行两项计时任务：

1. 产品经理从导入 HTML 到创建待评审版本并复制评审摘要，目标小于等于 3 分钟。
2. 研发从进入项目到确认当前基线并说出相对上一基线的三条主要变化，目标小于等于 10 秒。

每项至少由两名未参与实现的使用者完成。失败时记录停顿位置，优先调整信息层级和默认动作，不通过增加说明文字掩盖路径问题。

## 两期交付边界
