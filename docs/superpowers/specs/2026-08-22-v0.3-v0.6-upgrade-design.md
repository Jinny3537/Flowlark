# Flowlark v0.3-v0.6 全量升级设计

**状态**：已批准  
**日期**：2026-08-22  
**目标版本**：`v0.6.5`  
**当前基线**：`v0.2.6`

## 1. 目标

在不改变“本地软件 + Git 协作 + 纯文本数据”地基的前提下，一次推进并分阶段验收 `v0.3.x` 到 `v0.6.x`：

1. 研发和测试能在只读模式下携带原型上下文反馈问题。
2. 产品经理能用拖拽、粘贴、URL 和 watch 草稿箱快速收集原型。
3. 团队能按需求、迭代和交付快照组织同一批原型版本。
4. 基线与交付事件能进入现有 Issue 和通知平台。
5. 非技术成员在 macOS 上无需安装 Node 即可启动、初始化和更新 Flowlark。

最终版本号统一升级到 `v0.6.5`，但实现必须保留 `v0.3.6`、`v0.4.6`、`v0.5.5` 和 `v0.6.5` 四个可运行验收点。

## 2. 已确认决策

| 决策 | 结论 |
|---|---|
| 交付节奏 | 一次推进到 `v0.6.5`，内部按四个大版本分阶段实现和验收 |
| 架构路线 | 在现有 Node.js + Vue 3 + Git 文件存储架构内分域扩展 |
| 分发平台 | macOS 完整支持；Windows/Linux 只保留兼容边界 |
| Issue 平台 | GitHub、GitLab、Gitee；无 Token 或调用失败时降级为 Markdown |
| 密钥存储 | macOS 钥匙串；环境变量可覆盖；不落仓库明文文件 |
| 更新来源 | 可配置发布清单 URL，不绑定特定代码托管平台 |
| 外部验收 | 本地模拟服务做自动化端到端测试；真实凭据通过“测试连接”验证 |
| 桌面实现 | 薄 `.app` 启动器，内置 Node 运行时，不引入 Electron |

## 3. 产品边界

### 3.1 保持不变

- CLI、HTTP API 和 Web 工作台继续共用 `Hub` 作为唯一业务事实来源。
- Git 权限继续投影为 Flowlark 写权限，不新增账号体系。
- 原型、规格、需求、迭代和交付快照仍是可审阅的文本文件。
- 运行时业务依赖保持为零；外部 HTTP 调用使用 Node 内置 `fetch`。
- 原型预览继续使用独立端口和受限 iframe，避免原型脚本读取工作台数据。

### 3.2 明确不做

- 不做自建评论、聊天、审批或实时协同系统。
- 不镜像 GitHub、GitLab、Gitee 的完整 Issue 状态机。
- 不做工时、排期、燃尽图等项目管理能力。
- 不让通知失败回滚已经成功的基线或快照事务。
- 不在镜像模式下自动 merge、rebase、force pull 或 push。
- 不把启动器发展成第二套工作台 UI。

## 4. 总体架构

```text
Vue 工作台 ─┐
CLI ────────┼─> Hub / 权限门 ─> 领域模块 ─┬─> Git 跟踪数据
macOS 启动器 ┘                            ├─> 本机缓存 / 钥匙串
                                         └─> Issue / Webhook / 更新源
```

领域模块按责任拆分：

- **反馈与导入**：标注、截图授权、Markdown、Issue Provider、HTML/URL/watch。
- **需求与迭代**：需求实体、反向索引、里程碑、筛选、已存视图、交付包。
- **审阅与交付**：审阅状态、深链、快照、通知、影响面。
- **分发与运维**：首次向导、更新、镜像、跨仓库索引、诊断。

所有仓库写操作必须先通过现有 `Hub.#assertWritable()`。只读用户允许浏览、搜索、预览、创建本机反馈草稿、提交外部 Issue 和导出 Markdown，但不能修改仓库文件。

## 5. Schema 2 数据模型

### 5.1 磁盘结构

```text
repo/
├── flowlark.json                     schemaVersion: 2
├── projects/                         现有项目结构保持
│   └── <slug>/versions/<no>.json     增加 reviewStatus；requirements 归一为编号数组
├── requirements/
│   └── <code>/
│       ├── requirement.json
│       ├── spec.md
│       └── files/
├── milestones/
│   └── <name>.json
├── snapshots/
│   └── <name>.json
├── views/
│   └── team.json
└── .flowlark/
    ├── oplog.ndjson
    ├── backup/
    └── cache/
        ├── index.json
        ├── feedback/
        ├── external/
        ├── notifications.ndjson
        ├── updates/
        └── workspaces.json
```

`requirements/`、`milestones/`、`snapshots/` 和 `views/` 进入 Git。`.flowlark/cache/`、更新缓存、外部状态和未发送反馈都不进入 Git。

### 5.2 需求实体

```json
{
  "code": "REQ-0275",
  "title": "订单批量关闭",
  "description": "运营需要一次关闭多个超时未支付订单",
  "owner": "张小雨",
  "statusOverride": null,
  "external": {
    "provider": "github",
    "project": "owner/repo",
    "key": "275",
    "url": "https://github.example/owner/repo/issues/275"
  },
  "createdAt": "2026-08-22T09:00:00.000Z",
  "updatedAt": "2026-08-22T09:00:00.000Z"
}
```

版本只保存需求编号，反向关系通过扫描版本派生。需求状态默认派生：

| 状态 | 判据 |
|---|---|
| 未开始 | 没有关联版本 |
| 设计中 | 有关联版本，但没有任何关联版本成为基线 |
| 已定稿 | 至少一个关联版本成为所在项目基线 |
| 已交付 | 所有关联项目均存在被交付快照引用的确认版本 |

`statusOverride` 仅用于“暂缓”等人工例外，界面必须标记为手动状态。

### 5.3 迭代

```json
{
  "name": "2026-S12",
  "title": "订单批量操作迭代",
  "startAt": "2026-08-01",
  "endAt": "2026-08-21",
  "items": [
    { "requirement": "REQ-0275", "project": "order-center", "version": "v2.4" }
  ],
  "createdAt": "2026-08-22T09:00:00.000Z",
  "updatedAt": "2026-08-22T09:00:00.000Z"
}
```

迭代是可调整的范围容器，必须显式固定版本号，不使用“读取时取当前基线”的动态引用。

### 5.4 交付快照

```json
{
  "name": "2026-S12-review",
  "title": "S12 研发评审",
  "milestone": "2026-S12",
  "items": [
    { "requirement": "REQ-0275", "project": "order-center", "version": "v2.4" }
  ],
  "changesDigest": "sha256:...",
  "createdAt": "2026-08-22T09:00:00.000Z",
  "createdBy": "git-user@example.com"
}
```

快照创建后不可修改和删除，只能创建替代快照。冻结前必须验证：引用存在、版本未废弃、审阅状态为“已确认”。失败时一次返回全部阻塞项。

### 5.5 审阅状态

版本新增 `reviewStatus`：

- `pending`：新版本默认值。
- `confirmed`：可以进入交付快照。
- `questions`：存在未解决疑问。
- `obsolete`：版本被废弃时同步进入；恢复版本后回到 `pending`。

状态必须同时显示文字和颜色，不能只靠颜色表达。审阅状态属于可变流程元数据，不改变原型文件的不可变性。

### 5.6 已存视图

`views/team.json` 保存团队共享筛选条件，不保存结果：

```json
{
  "views": [
    {
      "id": "pending-review",
      "name": "本周待评审",
      "scope": "versions",
      "filters": { "reviewStatus": ["pending", "questions"], "updatedWithinDays": 7 }
    }
  ]
}
```

筛选结果始终实时计算，避免缓存与真实数据分叉。

## 6. v0.3.x：反馈闭环与上传

### 6.1 标注反馈

工作台提供“标注”模式，在 iframe 上层绘制透明选择层。选择框使用相对坐标 `x/y/width/height`，范围为 `0..1`，保证不同窗口尺寸下仍可定位。

反馈上下文包含：仓库标识、项目、版本、当前基线、需求编号、选择坐标、页面路径、变更摘要和创建时间。

截图通过浏览器 `getDisplayMedia()` 获取用户明确授权的当前标签页，再按选择坐标裁剪。用户拒绝授权或浏览器不支持时，反馈仍可提交，但只附深链和坐标，不把截图作为硬前置条件。

深链格式：

```text
#/projects/<slug>/versions/<version>?anchor=<base64url-json>
```

打开深链后工作台展示定位框，并允许一键进入标注上下文。

### 6.2 Markdown 降级

统一反馈模型先渲染成 Markdown，再由 Provider 转成 Issue 请求。Markdown 至少包含：标题、问题描述、需求、项目、版本、基线、深链、区域坐标、变更摘要和截图文件名。

Provider 未配置、连接失败、限流或远端返回错误时：

1. 保留本机草稿和截图。
2. 展示可复制、可下载的 Markdown。
3. 返回可理解错误和“重试创建 Issue”操作。

### 6.3 Issue Provider

Provider 使用统一接口：

```js
{
  testConnection(config),
  createIssue(config, feedback),
  searchIssues(config, query),
  buildIssueUrl(config, issue)
}
```

首批实现 GitHub、GitLab、Gitee。每个 Provider 负责自己的认证头、项目标识、标签和附件限制；业务层只处理统一反馈模型。

密钥优先级：环境变量 > macOS 钥匙串。环境变量命名使用 `FLOWLARK_GITHUB_TOKEN`、`FLOWLARK_GITLAB_TOKEN`、`FLOWLARK_GITEE_TOKEN`。钥匙串不可用时不写明文回退文件。

需求详情中的反馈列表通过 Provider 标签和项目/版本上下文查询，结果只缓存到本机，不写入只读仓库。

### 6.4 原型导入

Web 新建版本入口统一支持：

- 拖拽一个 HTML 文件。
- 从剪贴板粘贴 HTML 文件或 HTML 源码。
- 输入 HTTP/HTTPS URL。
- 从 watch 草稿箱选择已收集文件。

文件和源码自动读取 `<title>` 作为建议标题，用户仍可修改。导入继续遵守现有文件大小、版本号、变更日志和基线规则。

URL 导入必须：

- 只允许 `http:` 和 `https:`。
- 拒绝 URL 用户信息、本机名、环回、链路本地、私网和保留地址。
- DNS 解析后校验所有返回地址。
- 每次跳转重新解析并校验，最多五次。
- 限制连接时间、总时间、响应大小和 HTML Content-Type。
- 下载到临时文件，完整校验通过后才进入版本创建事务。

### 6.5 watch 草稿箱

保留现有 `flowlark watch`，新增稳定写入、去重和草稿箱视图：

- 文件写入稳定窗口后再收集，避免半文件。
- 内容哈希去重，同一文件连续保存不会重复归档。
- 自动归档版本默认 `pending` 和草稿状态。
- 草稿箱可补标题、需求、变更日志并转为正式版本。
- 失败项保留原因和重试操作。

## 7. v0.4.x：需求、迭代与检索

### 7.1 需求视图

导航增加“需求”。列表支持状态、负责人、迭代、项目、外部平台筛选。详情页展示：需求说明、关联项目与版本、跨项目时间线、聚合变更、附件、外部链接和反馈列表。

反向索引写入 `.flowlark/cache/index.json`，包含输入文件指纹。缓存缺失或指纹变化时重建；删除整个缓存后结果必须完全一致。

### 7.2 迭代视图

导航增加“迭代”。迭代详情展示版本清单、当前基线差异、审阅状态、未定稿或已废弃告警。迭代可以编辑，不承担不可变交付证据职责。

### 7.3 交付包

需求或迭代可导出自包含静态目录：索引页、离线原型、规格、变更日志、附件和清单 JSON。断网双击 `index.html` 必须可浏览，不依赖 Flowlark 服务。

### 7.4 搜索和已存视图

全局搜索升级为面板，支持关键词、标签、审阅状态、时间、需求号、迭代、附件类型和项目筛选。结果覆盖项目、版本、需求、迭代和快照，并按对象类型分组。

团队共享已存视图进入 Git；个人最近筛选只保留浏览器本地存储。

## 8. v0.5.x：审阅、交付与通知

### 8.1 Webhook Provider

首批实现企业微信、钉钉、Slack。统一接口：

```js
{
  testConnection(config),
  send(config, event, renderedMessage)
}
```

仓库只保存 Provider 类型、启用事件和消息模板；Webhook URL、签名密钥进入钥匙串。支持 `baseline.created`、`snapshot.created` 和 `review.questions` 三类事件。

通知在主事务成功后执行。失败不会回滚基线、状态或快照，而是追加到本机 `notifications.ndjson` 重试队列。队列使用事件幂等键，手动重试不会重复发送已成功事件。

### 8.2 通知模板

模板只支持固定变量替换，不执行任意 JavaScript。变量包括项目、版本、需求、迭代、快照、变更条数、审阅状态和深链。设置页提供预览与“测试连接”。

### 8.3 快照和影响面

交付页负责创建和查看不可变快照、导出交付包、复制链接和重试通知。

影响面通过历史变更日志的“类型 + 位置”匹配关联需求和版本。结果必须展示来源记录，不输出无法解释的评分；它只提示潜在回归范围，不自动修改需求关联。

## 9. v0.6.x：macOS 分发与多仓库

### 9.1 Flowlark.app

构建产物为薄 macOS `.app`：

```text
Flowlark.app/Contents/
├── Info.plist
├── MacOS/flowlark-launcher
└── Resources/
    ├── runtime/node
    ├── app/bin/
    ├── app/src/
    └── app/web/dist/
```

启动器负责选择运行时、读取本机工作区配置、启动 Flowlark、等待健康检查并打开默认浏览器。业务 UI 仍由现有 Vue 工作台提供。

验证时从 `PATH` 移除系统 Node，确保 `.app` 仅使用内置运行时启动。

### 9.2 首次使用向导

首次启动流程：选择已有仓库或输入 Git URL → 选择本地目录 → clone/pull → 校验 Schema → 探测读写权限 → 保存工作区 → 打开项目列表。

macOS 文件夹选择由启动器调用系统选择器；Web 页面不直接读取任意本机目录。SSH 和 HTTPS Git URL 都允许，认证继续交给系统 Git/SSH Agent。

### 9.3 更新清单

发布清单格式：

```json
{
  "version": "0.6.5",
  "publishedAt": "2026-08-22T09:00:00.000Z",
  "url": "https://downloads.example/Flowlark-0.6.5.zip",
  "sha256": "<64 lowercase hex characters>",
  "minSchemaVersion": 2,
  "notesUrl": "https://downloads.example/flowlark/0.6.5"
}
```

启动时后台检查，不阻塞工作台。下载完成后必须校验 SHA-256，再提示用户安装；校验失败、网络失败或版本不兼容时保留当前版本。首版不做静默替换正在运行的 `.app`。

### 9.4 只读镜像

镜像工作区永久以只读 Hub 启动，按配置周期执行 `git fetch` 和 `git pull --ff-only`，同时提供手动刷新。工作区不干净、非快进或冲突时停止自动同步并展示诊断，不覆盖本地文件。

### 9.5 跨仓库索引

工作区列表与统一索引只存本机。索引记录仓库路径、显示名、最近状态和对象摘要；搜索结果带仓库来源并跳转到对应实例。单仓库业务文件不保存其他仓库路径。

## 10. 工作台信息架构

主导航调整为：

1. 项目：按产品原型查看版本。
2. 需求：按业务需求查看跨项目演进。
3. 迭代：查看本轮范围和定稿风险。
4. 交付：查看冻结快照、导出和通知。

全局搜索、Git 状态、只读状态保留在顶部；操作日志、回收站和设置作为辅助入口。选中态继续使用浅背景、边框和文字权重，不增加侧边色条。

新增关键界面：

- 工作台标注层与反馈抽屉。
- 统一导入弹窗和 watch 草稿箱。
- 需求列表与详情。
- 迭代列表与详情。
- 交付快照列表与详情。
- 搜索筛选面板和已存视图。
- 集成、通知、更新和工作区设置。
- 首次使用向导与镜像诊断页。

界面遵循 `design-system/flowlark/MASTER.md`：亮色生产力工作台、Ant Design Vue 4、设计 Token、无 emoji 图标、焦点可见、状态不只靠颜色、加载超过 300ms 有反馈、桌面与移动无重叠。

## 11. 迁移

Schema 1 到 2 的迁移流程：

1. 检查 Git 工作区干净；不干净则拒绝迁移。
2. 备份受影响文件到 `.flowlark/backup/schema-1-<timestamp>/`。
3. 扫描版本中的需求对象，按编号去重并生成需求实体。
4. 标题冲突采用时间线上最新版本的值，其他值写入迁移报告。
5. 将版本需求字段改为编号数组，缺失 `reviewStatus` 的版本设为 `pending`。
6. 写入 `schemaVersion: 2` 并重建索引。
7. 任一步失败则从备份原子回滚。

提供迁移预检、正式迁移和回滚命令。迁移不自动提交 Git，用户必须能够审阅 diff。

## 12. 错误与恢复规则

| 场景 | 行为 |
|---|---|
| Issue 创建失败 | 保留草稿和截图，生成 Markdown，允许重试 |
| Webhook 失败 | 主事务成功，进入幂等重试队列并提示 |
| URL 命中私网或重定向到私网 | 拒绝导入并说明被拦截目标 |
| 钥匙串不可用 | 仅使用环境变量，不写明文密钥 |
| 索引损坏 | 删除并重建，不影响源数据 |
| 快照存在未确认版本 | 拒绝冻结并列出全部阻塞版本 |
| 镜像非快进或冲突 | 停止同步、保持只读、展示恢复步骤 |
| 更新清单或 SHA-256 无效 | 保留当前版本，不执行安装 |
| 启动端口占用 | 自动选择可用端口并显示实际地址 |

## 13. 测试策略

### 13.1 Core 单元测试

- Schema 迁移、冲突报告、失败回滚。
