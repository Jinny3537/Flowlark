## 现有实现与影响

本次静态检查 `src/core/net.js`、`src/server/index.js`、`src/server/routes.js` 与上一轮检查的 `src/core/permissions.js`：

- 当前 LAN 写保护是路由前按 HTTP 方法整体拦截；要让研发和测试写入进度、反馈与验收，需增加按具体操作判断的能力。
- `/api/health` 目前主要返回 `canWrite`；角色模式需要表达各类操作权限，单一布尔值不够。
- Git 权限目前判断仓库能否写入，不代表访问者属于哪个业务角色。
- 不能仅关闭 LAN 只读来实现团队模式，否则会同时放开不属于研发或测试职责的写接口。
- 统一主机需要保存协作写入，不能直接采用现有永久只读镜像模式承载这些操作。

这些是实现约束，并不意味着本次已经完成代码改造。当前工作区有其他 UI 改动，本次仅修改规划文档。

## 方案与实现建议

### 协作路径

产品本机编辑需求与原型，通过 Git 交换数据；统一主机提供团队浏览、进度反馈、问题提交和验收入口。主机上的协作记录也需要可持久化并回到产品工作区。

建议第一阶段使用明确的人工 Git 同步入口，展示上次成功时间、待同步变更与冲突处理状态。自动同步频率、谁能触发同步、主机协作记录如何合并尚待确定。Git 同步成功不等同于验收通过或正式发版。

### 角色选择与记忆

已确认流程：远程首次访问 → 选择游客、研发或测试 → 按浏览器访客标识保存角色 → 后续访问恢复 → 如需变更由主机调整。远程选择列表不提供产品角色，也不提供自行切换角色入口。主机调整后，后续请求必须按新角色判断权限。

建议服务端保存访客标识与有效角色映射，浏览器只持有访客标识；不信任请求中自报的角色。选角接口也必须限制首次选择，不能通过重复请求覆盖已分配角色。具体会话存储和刷新实现由研发设计。

IP 仅用于主机访客列表的辅助识别。同 IP 的不同浏览器分别记忆角色；浏览器标识仍存在时，IP 变化不改变角色。

无登录且首次自主选角属于可信团队的操作分工，不能证明真实人员身份。清除浏览器数据或更换设备后的识别与重置处理仍需细化，不能宣称主机改角能跨设备永久约束同一个人。

### 权限矩阵的已知边界

| 能力 | 游客 | 产品 | 研发 | 测试 |
|---|---|---|---|---|
| 查看原型与资料 | 全部项目 | 与产品职责匹配，项目范围待确认 | 已确认可查看交付材料 | 测试所需查看范围待确认 |
| 管理需求与原型 | 待明确是否禁止 | 已确认 | 未授权，建议禁止 | 未授权，建议禁止 |
| 正式发版 | 未授权，建议禁止 | 已确认，沿用既有发版门禁 | 未授权，建议禁止 | 未授权，建议禁止 |
| 反馈开发进度 | 待确认 | 待确认 | 已确认 | 待确认 |
| 提交问题 | 待确认 | 待确认 | 待确认 | 已确认 |
| 提交验收结果 | 未授权，建议禁止 | 沿用既有规则的范围待确认 | 沿用既有规则的范围待确认 | 已确认；不得由此推导可替代其他角色签收 |
| 下载材料、发表评论 | 允许 | 待确认 | 待确认 | 待确认 |
| 首次远程自选 | 允许 | 不允许 | 允许 | 允许 |
| 自行切换已选角色 | 不允许 | 不适用远程首次选角 | 不允许 | 不允许 |

仅主机可调整访问者角色；不因为远程选择了某个业务角色就获得主机管理权。主机管理入口与操作者识别方式仍需细化。

确认后的权限需要同时落实到页面入口、服务端操作及数据范围。角色授权不能绕过冻结、发版、验收、Git 只读等现有业务约束。

## 已确认规则的验收条件

- 远程首次选择仅包含游客、研发、测试；直接请求分配产品角色被服务端拒绝。
- 角色选择成功后再次访问恢复原角色；重复调用选角接口不能自行改角。
- 主机调整角色后，访问者后续操作按新角色判定，不能用旧页面或自报角色绕过。
- 同 IP 下两个不同浏览器分别保持自己的角色；浏览器标识未变时，换 IP 不改变角色。
- 游客无需分享链接即可浏览全部项目、发表评论和下载材料。

## 后续验证关注点

- 浏览器标识丢失、访客重置与旧记录处理。
- 直接调用不允许的写接口时，服务端仍能拒绝。
- 研发和测试的协作写入不连带开放原型删除、基线修改、系统配置等操作。
- 产品本机与团队主机同步后，原型、反馈、进度和验收记录不丢失；冲突可处理。
- 保留既有冻结、正式发版、历史材料和验收状态约束。
